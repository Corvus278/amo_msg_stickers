## Context

Мотивация — proposal.md («Why»), требование — `specs/gif-search/spec.md`.

- `sources/gifs.ts` выбирает версию для отправки `pickVariant` — первую по списку имён, прошедшую гард формы и сетевую
  политику: GIPHY `['downsized', 'original']`, KLIPY `['gif', 'tinygif']`. Вес версии гарды не читают.
- KLIPY отдаёт только форматы из `media_filter` (сейчас `gif,tinygif`); без фильтра — 16 форматов.
- `app.ts` качает выбранную версию `host.fetchBlob(url, MAX_REMOTE_GIF_BYTES)` (8 МБ, константа в `app.ts`), проверяет
  `toCheckedGifFile` (`inspectGif`) и отправляет как есть, сколько бы она ни весила до 8 МБ.
- Штатная конвертация `toStickerGif(blob, 'image')` (`convert.ts`) GIF не больше 2 МБ без подписи отдаёт как есть,
  тяжелее — перекодирует лестницей сторон до `MAX_GIF_BYTES` (2 МБ, `sidePick.ts`, одна константа на весь код).

Замер ответов API (запрос «ган вест», 24 элемента, 2026-09-27):

- KLIPY: вес — число `size` у каждого формата. `gif` — 0,4–17,6 МБ (у 11 из 24 больше 8 МБ), `mediumgif` — 0,4–10,7 МБ
  (сторона бывает больше, чем у `gif`: 640 против 498), `tinygif` — 0,04–1,4 МБ, `nanogif` — до 0,4 МБ.
- GIPHY (GIF и стикеры): вес — строка `size` у каждого GIF-рендишна. `downsized` — до ~1,9 МБ, `original` — до 11 МБ,
  `downsized_medium` / `downsized_large` — 1–7 МБ, `fixed_height` / `fixed_width` — 0,2–2,4 МБ.

## Goals / Non-Goals

**Goals:**

- выбор версии по весу — чистая функция без DOM, покрытая юнит-тестами;
- GIF из поиска тяжелее 2 МБ пережимается при любом пути: выбор по весу, выдача без весов, недавние GIF. Предел
  пережатия — штатная лестница сторон: на 256 px результат уходит как есть, даже тяжелее 2 МБ (решение пользователя,
  как у своих стикеров).

**Non-Goals:**

- свой лимит длительности и кадров для GIF из поиска: пережатие — штатное, до 4 с и 100 кадров (решение пользователя);
- перевыбор версии у недавних GIF: запись хранит одну ссылку, выдача с весами не перезапрашивается;
- отдельный индикатор конвертации на отправке: статус «Отправляю…» и спиннер ячейки остаются как есть.

## Decisions

### 1. Правило выбора: «самая тяжёлая до 2 МБ», а не «самая тяжёлая до 8 МБ»

Среди версий с известным весом берётся самая тяжёлая из не больше `MAX_GIF_BYTES` — она уходит без конвертации. Если
таких нет — самая лёгкая из не больше `MAX_REMOTE_GIF_BYTES`: меньше качать и быстрее пережимать. Если и таких нет —
самая лёгкая из всех с весом: скачивание честно оборвётся на лимите с «Файл больше 8 МБ». Равный вес — первая по списку
кандидатов.

Альтернатива из текста issue — «самая тяжёлая до 8 МБ, тяжелее 2 МБ пережимается» — отклонена пользователем: почти
каждая GIF KLIPY и многие GIPHY (`original` 4–8 МБ вместо `downsized`) шли бы через конвертацию — секунды ожидания и
обрезка до 4 с вместо мгновенной отправки целиком. Вес — прокси качества: у одного GIF тяжелее версия — больше сторона
или кадров.

### 2. Кандидаты по источникам

- GIPHY: `original`, `downsized_large`, `downsized_medium`, `downsized`, `fixed_height`, `fixed_width`,
  `fixed_height_small`, `fixed_width_small`. Не берутся `*_still` (один кадр), `*_downsampled` и `preview_gif`
  (прореженные кадры), `*_mp4` / `webp` (не GIF).
- KLIPY: `gif`, `mediumgif`, `tinygif`, `nanogif`; `media_filter` = `gif,mediumgif,tinygif,nanogif`. Превью — прежние
  `tinygif`, затем `gif`.

Порядок списка — от крупной версии к мелкой: он решает равенство веса и служит фолбэком.

### 3. Выдача без весов — прежний порядок имён

Вес читается необязательным полем: GIPHY — строка с положительным числом, KLIPY — положительное число; иное — «веса
нет», элемент выдачи при этом не отбрасывается (гарды формы не ужесточаются). Выбор по весу видит только кандидатов
с весом, прошедших гард и сетевую политику. Если таких нет, работает прежний `pickVariant` с прежними списками
(`downsized`, `original` / `gif`, `tinygif`) — выдача без весов ведёт себя как сейчас.

### 4. Пережатие на отправке, по фактическому весу файла

В ветке `remote` `app.ts`: скачать → `toCheckedGifFile` (байты — GIF, иначе `SendError`) → если файл тяжелее
`MAX_GIF_BYTES`, `toStickerGif(file, 'image')` и `toGifFile(результат, имя)`. Решение — по весу скачанного файла, а не
по весу из выдачи: так пережимается и GIF из выдачи без весов, и недавняя GIF, сохранённая со ссылкой на тяжёлую
версию, и версия, чей вес в ответе разошёлся с фактом. Проверка GIF — до конвертации: HTML-страница ошибки получит
понятное «Файл не похож на GIF», а не ошибку декодера.

Альтернатива — флаг «нужно пережать» в `RemoteGif` по весу из выдачи — отклонена: меняет формат записи недавних и не
покрывает выдачу без весов.

### 5. Лимит скачивания — в сетевой политике

`MAX_REMOTE_GIF_BYTES` переезжает из `app.ts` в `net.ts` рядом с `BYTES_IN_MB`: его читают и отправка (`app.ts`), и выбор
версии (`sources/gifs.ts`). `MAX_GIF_BYTES` источники импортируют из `sidePick.ts` — модуль без DOM и зависимостей.

## Risks / Trade-offs

- [Мелкая версия вместо крупной: у KLIPY «ган вест» уходит `tinygif` 165×294, а не `gif` 281×498] → осознанный выбор
  пользователя (Decision 1): отправка мгновенная, анимация целиком. Сторона не меньше, чем дала бы конвертация
  13-мегабайтного `gif` до 2 МБ.
- [Конвертация на отправке занимает секунды; попап, открытый наведением, может закрыться уходом курсора] → отправка
  доживает и без открытого попапа, как и нынешнее скачивание 8 МБ; путь редкий — версия до 2 МБ есть почти всегда.
- [Пережатая GIF длиннее 4 с обрезается] → принято (Non-Goals); касается только GIF без версии до 2 МБ.
- [Вес в ответе API расходится с фактом] → решение о пережатии — по факту (Decision 4), лимит 8 МБ обрывает скачивание
  независимо от ответа.
- [`app.ts` тянет `convert.ts` в граф импорта] → `convert.ts` уже в бандле ядра через `useStickerDraft`; юнит-тестов
  `app.ts` нет, `vi.mock` не нужен.

## Migration Plan

Схема IndexedDB и `RemoteGif` не меняются. Недавние GIF со ссылкой на версию 2–8 МБ после обновления отправляются
пережатыми. Откат — revert PR.
