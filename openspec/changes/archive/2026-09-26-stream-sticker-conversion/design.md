## Context

Мотивация — в `proposal.md` (Why). Текущее устройство `src/core/convert.ts`:

- `sourceFrames` (видео, `.tgs`, картинка) возвращает `FrameSet` — массив `ImageData` всех кадров в 512 px;
- `encodeWithinBudget` кодирует набор целиком, при весе больше 2 МБ зовёт `scaleFrames` (полная копия набора в
  меньшем размере) и кодирует снова — до трёх раз, исходный набор жив до конца;
- `indexFrame` (quantize rgb565, `applyPalette`, дизеринг Байера) и `gif.writeFrame` идут подряд на главном потоке,
  без единой уступки;
- `videoFrames` в `finally` отзывает object URL, но `<video>` держит загруженные данные, а `once` при таймауте не
  снимает слушатель.

Ограничения окружения:

- код живёт в чужой странице: content script MV3 (изолированный мир) и userscript (`@grant none`, контекст
  страницы, в том числе Electron-клиент amo);
- Worker по `chrome-extension://` URL со страницы не запустить; у `web.amo.tm` нет CSP (проверены заголовки и
  `<meta>`), поэтому остаётся Worker из blob URL;
- `gifenc` кодирует инкрементально: `writeFrame` по одному кадру, держать набор ему не нужно;
- декод VP9 делает браузер, кадры видео достаются только seek-ом `<video>` и `drawImage`;
- юнит-тесты идут в `node` без DOM: чистая логика должна жить отдельно от canvas, `<video>` и Worker.

## Goals / Non-Goals

**Goals:**

- в памяти одновременно не больше нескольких несжатых кадров стикера — окно обратного давления плюс кадр на холсте;
- тяжёлая работа (квантизация, дизеринг, LZW) — вне главного потока;
- в типичном случае один полный проход по источнику вместо до четырёх;
- тот же вид GIF, что сейчас, при том же размере: палитра, прозрачность, дизеринг, задержки не меняются;
- API `toStickerGif` / `detectKind` / `captionDecorator` для `telegram.ts` и `useStickerDraft` не меняется.

**Non-Goals:**

- уменьшение веса GIF (lossy LZW, межкадровая дельта, обрезка до изменившегося прямоугольника);
- WebAssembly;
- параллельная конвертация нескольких стикеров: импорт пака остаётся последовательным;
- изменение схемы IndexedDB и формата хранимых стикеров.

## Decisions

### 1. Источник кадров — объект с произвольным доступом, а не массив кадров

Каждый вид источника открывается один раз на конвертацию и отдаёт:

- размер (вписанный в 512 px) и план кадров — список `{ позиция, задержка }`, где позиция — время для видео, номер
  кадра для `.tgs` и `ImageDecoder`;
- `draw(i, ctx, w, h)` — нарисовать кадр `i` в заданный контекст заданного размера;
- `dispose()` — освободить ресурсы (зовётся в `finally` конвертации).

План считается до захвата по тем же правилам, что сейчас (25 fps, 4 с, 100 кадров, шаг `.tgs` от исходных fps,
задержки `ImageDecoder` с нижней границей 20 мс). Проход — это цикл по плану: `draw` → подпись → `getImageData` →
отдать кадр кодировщику. Пробный проход берёт подмножество плана, повторный — тот же план при меньшем размере.

- видео: `<video>` живёт все проходы, `draw` = seek + `drawImage(video, 0, 0, w, h)`;
- `.tgs`: анимация рендерится на своём холсте в размере источника, `draw` = `goToAndStop` + `drawImage` этого
  холста в целевой — второй экземпляр lottie на каждый размер не нужен;
- картинка через `ImageDecoder`: `draw` = `decode({ frameIndex })` + `drawImage` + `close()` кадра;
- фолбэк `createImageBitmap`: один кадр, битмап живёт до `dispose`.

Подпись рисуется на целевом холсте после масштабирования, а не до него. Размер подписи задан долями высоты
(`captionDecorator`), поэтому вид тот же, а текст на 256 px не мылится от даунскейла.

*Альтернатива:* асинхронный генератор кадров, пересоздаваемый на каждый проход. Отклонена: для повторного прохода
пришлось бы заново открывать видео и ждать `loadeddata`, а пробный проход по подмножеству кадров выразить сложнее.

### 2. Потоковый кодировщик — чистый модуль без DOM

`indexFrame` и запись кадра переезжают в отдельный модуль потокового кодировщика: создаётся на
`{ width, height, isAnimated }`, принимает `write(rgba, delay)`, отдаёт текущий `byteLength` и `finish()` → байты
GIF. Он не знает ни про canvas, ни про Worker и одинаково работает в Worker-е, на главном потоке и в `node` — там
его и тестируют.

### 3. Кодирование в Worker из встроенного бандла

- Точка входа Worker-а собирается `build.mjs` отдельным esbuild-вызовом (`write: false`, IIFE, `chrome120`,
  минификация вне `watch`). Плагин отдаёт результат виртуальным модулем с именованным экспортом строки кода; входные
  файлы Worker-а идут в `watchFiles`, чтобы `pnpm watch` пересобирал его вместе с ядром.
- Ядро запускает Worker через `new Worker(URL.createObjectURL(new Blob([code])))`, URL отзывается сразу после
  старта.
- Протокол: `start { width, height, isAnimated }` → `frame { rgba, delay }` с передачей буфера (transfer, без
  копии) → ответ `ack { byteLength }` на каждый кадр → `finish` → `done { bytes }` с передачей буфера. Ошибка
  кодирования → `error { message }`, конвертация падает с ней.
- Один Worker на вызов `toStickerGif`: обслуживает пробный и все полные проходы, в `finally` — `terminate()`.
  Память кодировщика гарантированно уходит вместе с Worker-ом, между стикерами пака ничего не копится; цена —
  разбор бандла Worker-а на каждый стикер (десятки мс), для последовательного импорта это незаметно.

*Альтернатива:* передавать в Worker `ImageBitmap` и снимать RGBA на `OffscreenCanvas` внутри. Отклонена: подпись
рисуется `CanvasRenderingContext2D` на главном потоке всё равно, а `getImageData` кадра 512 px на холсте с
`willReadFrequently` стоит единицы мс. Передача готового RGBA оставляет Worker без DOM и делает его код тем же
самым, что и фолбэк.

*Альтернатива:* один долгоживущий Worker на страницу. Отклонена: экономит только разбор бандла, зато требует
сброса состояния между стикерами и не даёт простой гарантии освобождения памяти.

### 4. Обратное давление

Захват (seek и `drawImage`) может идти быстрее кодирования. Клиент Worker-а держит в полёте не больше 2 кадров:
`write` ждёт `ack` самого старого, когда окно заполнено. Без этого кадры копились бы в очереди сообщений Worker-а,
и пик памяти вернулся бы к размеру всего набора.

### 5. Фолбэк без Worker

Если конструктор Worker-а бросает (CSP страницы, политика изолированного мира) или Worker падает `error` до
первого `ack`, конвертация продолжается тем же потоковым кодировщиком на главном потоке, с уступкой потока
(`setTimeout(0)`) после каждого кадра. Неудача запоминается на время жизни страницы: следующие стикеры сразу идут в
фолбэк, без повторной попытки. Ошибка Worker-а после первого `ack` — это ошибка конвертации, а не повод для
фолбэка: иначе при падении по памяти кадры закодировались бы второй раз на главном потоке.

Оба варианта — одна абстракция «приёмника кадров» (`write` / `finish`), конвейеру всё равно, где идёт
кодирование.

### 6. Выбор размера по пробным кадрам

- Если в плане больше `SAMPLE_FRAMES` (8) кадров и большая сторона источника больше 256 px, до полного прохода
  идёт пробный: 8 равномерно взятых кадров плана в размере источника, в отдельный поток кодировщика; нужен только
  `byteLength` после последнего кадра, `finish` не зовётся.
- Оценка для стороны `s`: `sampleBytes / 8 × N × (s / side)² × SAFETY`, где `N` — число кадров плана, `side` —
  сторона источника. Вес LZW-потока растёт примерно с числом пикселей; `SAFETY` (стартовое значение 1,1)
  компенсирует заголовки и разброс кадров.
- Ряд сторон — сторона источника (вписанная в 512 px), затем меньшие неё из 384 / 320 / 256, как в лестнице сейчас.
  Выбирается наибольшая сторона ряда с оценкой не больше 2 МБ; если такой нет — последняя.
- Полный проход кодирует в выбранном размере. Итог тяжелее 2 МБ → следующая меньшая сторона, новый проход по
  источнику. Результат прошлой попытки выбрасывается до начала следующей.
- При 8 и меньше кадрах или стороне 256 и меньше пробного прохода нет: полный проход сразу в стороне источника,
  дальше та же лестница.

Выбор стороны — чистая функция от `(sampleBytes, sampleCount, frameCount, side)`, тестируется в `node`.

*Альтернатива:* пробные кадры во всех четырёх размерах. Точнее, но стоит как ~треть полного прохода, а лестница
повторных проходов и так гарантирует лимит. *Альтернатива:* кодировать сразу в 256 и подбирать вверх — худшее
качество у стикеров, которые влезли бы в 512.

### 7. Освобождение `<video>` и ожидание событий

- `dispose` видео-источника: `video.removeAttribute('src')`, `video.load()`, `URL.revokeObjectURL(url)` —
  при любом исходе, включая ошибку до `loadeddata`.
- Ожидание события элемента (`loadeddata`, `seeked`) снимает свой слушатель при срабатывании, таймауте и ошибке и
  сразу отклоняется по событию `error` элемента, не дожидаясь таймаута в 10 с.

### 8. Раскладка модулей

- `convert.ts` — оркестрация: passthrough GIF, открытие источника, пробный проход, лестница размеров, `finally`
  с `dispose` и `terminate`; публичный API прежний.
- новые модули ядра: источники кадров, потоковый кодировщик, выбор стороны, приёмник кадров (Worker и фолбэк),
  точка входа Worker-а; типы — в соседних `*.types.ts`, как принято в проекте.
- `src/types.d.ts` — описание виртуального модуля с кодом Worker-а. Модуль, который его импортирует, юнит-тесты не
  грузят (vitest не знает плагина `build.mjs`): тестируются кодировщик и выбор стороны, которые от него не зависят.

## Risks / Trade-offs

- [Оценка систематически занижает вес] → лишние полные проходы: CPU и время, но не память. Митигация — замер на
  `video_gachi`, подбор `SAFETY` по результату.
- [Оценка завышает вес] → стикер получает меньшую сторону, чем мог бы. Митигация — тот же замер; допустимая
  погрешность записана в сценарии спеки («384 или 320 px»).
- [Blob-Worker не запускается из изолированного мира content script или его закроет будущая CSP amo] → фолбэк на
  главном потоке: медленнее, но с уступками и без падения. Проверка — первой задачей, до переноса кодирования.

  *Спайк 2.1, стенд (2026-09-26, Chrome 153, мир страницы `dev/harness.html`):* работает.
  `new Worker(URL.createObjectURL(new Blob([code])))` не бросает, URL отозван сразу после конструктора — Worker
  всё равно стартует; `postMessage` с transfer буфера 512×512×4 — исходный `ArrayBuffer` отсоединён
  (`byteLength === 0`), Worker получил 1 048 576 байт и вернул свой буфер тоже transfer-ом. У `https://web.amo.tm/`
  на эту дату нет CSP ни заголовком, ни `<meta>` — `worker-src` страницы blob-Worker не закрывает.

  *Спайк 2.1, живой amo (2026-09-26, Chrome, `web.amo.tm`, сверка пользователя):* работает в обеих целях —
  расширение (content script, изолированный мир) и userscript в Tampermonkey (`@grant none`): конвертация проходит,
  импорт быстрее прежнего, вкладка не падает по памяти. Worker из blob URL — основной путь для обеих целей, фолбэк
  группы 4 — запасной. Импорт пака Telegram в userscript упирается в CORS скачивания файла — это устройство цели, не
  Worker-а (issue #15).
- [Один кадр кодируется на главном потоке дольше 1 с в фолбэке] → на 512 px это не ожидается; проверяется
  профилем на стенде. Если подтвердится — дробить `indexFrame` по строкам — отдельная задача.
- [gifenc попадает в бандл дважды: в Worker и в ядро для фолбэка] → десятки КБ к `content.js` и userscript,
  приемлемо.
- [Повторный проход по видео снова декодирует его seek-ами] → время растёт на каждую ступень лестницы; ради этого
  и нужна оценка, делающая лестницу редкостью.
- [Подпись рисуется после масштабирования] → на исходниках меньше 512 px и на ступенях лестницы подпись
  рендерится в целевом размере: вид не меняется, текст резче.

## Migration Plan

Миграций данных нет: схема IndexedDB и формат стикеров прежние, уже импортированные паки не трогаются. Версия —
минор, `0.5.0` в трёх местах. Откат — revert PR.

## Open Questions

- Точность оценки и значение `SAFETY` на `video_gachi` — замер при реализации (задача в `tasks.md`).

  *Ответ (7.2, 2026-09-26, headless Chrome 153, фолбэк на главном потоке, все 45 стикеров пака):* `SAFETY`
  остаётся 1,1. Один полный проход — у 44 из 45 стикеров, второй — у одного (№ 31: оценка 1937 КБ при 320 px,
  факт 2050 КБ, итог 1400 КБ при 256 px). Итоговые стороны: 256 px — 41, 320 — 2, 384 — 2; тяжелее 2 МБ и при 256 px
  — 18 из 45 (сценарий «Лимит недостижим»).

  Ошибка оценки систематическая, но зависит от стороны, а не постоянна. Отношение фактического веса к оценке без
  `SAFETY` по всем 45 стикерам, закодированным на каждой стороне ряда: 512 px — 0,99–1,02 (медиана 1,00), 384 —
  1,04–1,10 (1,07), 320 — 1,10–1,18 (1,13), 256 — 1,16–1,30 (1,21). Масштаб по площади занижает вес меньших
  сторон: мелкий кадр жмётся хуже на пиксель. Один множитель это не исправляет, а на 256 px оценка ничего не решает
  — это последняя сторона ряда.

  Перебор `SAFETY` на тех же фактических весах: 1,00 — пять лишних проходов; 1,06–1,16 — один (№ 31), сторона
  нигде не хуже достижимой; 1,17–1,18 — ни лишних проходов, ни потерь; от 1,19 — № 10 уходит с 320 на 256 px, от
  1,24 — ещё № 35 с 384 на 320. Окно 1,17–1,18 держится на двух стикерах, и выход из него вверх стоит качества
  навсегда, а вниз — одного лишнего прохода: время, не память. Поэтому 1,1 из середины устойчивого диапазона.
  Точнее оценку сделал бы показатель степени меньше 2 в масштабе по стороне — это смена формулы D6, не `SAFETY`.

  Цена лестницы по памяти: пик кучи после `gc()` у одного прохода на 512 px и у трёх–четырёх проходов
  (512 → 384 → 320 → 256) одинаков — 41 МБ (№ 00, № 12) и 38 МБ (№ 44), RSS рендерера в тех же окнах — 772–815 МБ
  без прогревочного окна (672 МБ) у обоих вариантов (сценарий «Повторная попытка по размеру»). Самая длинная задача
  главного потока — 218 мс против 858–4702 мс базовой линии 1.3.
- Доля времени `indexFrame` против seek и `getImageData` — профиль при реализации; на подход не влияет, нужен для
  проверки бюджета главного потока в фолбэке.
