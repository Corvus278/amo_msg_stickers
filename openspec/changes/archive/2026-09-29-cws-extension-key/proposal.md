## Why

Расширение отправлено в Chrome Web Store (issue #51). ID распакованного расширения Chrome считает от пути к папке, а
ID из стора — от ключа, который CWS выдал при первой загрузке. Пока ключа в `manifest.json` нет, архив из релиза и
версия из стора — два разных расширения: у каждого своё хранилище, и ключи GIF и токен бота не переходят между ними, а
распаковка архива в другую папку ставит расширение заново с пустыми «Настройками».

## What Changes

- В `manifest.json` расширения появляется поле `key` — публичный ключ из панели CWS. Архив из релиза, распакованный в
  любую папку, получает тот же ID, что версия из стора.
- **BREAKING** (однократно): у тех, кто ставил расширение из архива без ключа, после обновления меняется ID — ключи
  GIF и токен бота вводятся заново. Стикеры, паки и недавние не пропадают: они в IndexedDB на домене amo. Это
  пишется в теле PR, из которого генерируются заметки релиза.
- Тест фиксирует ключ: из него вычисляется ID, и он должен совпасть с ID карточки в сторе.
- Вне задачи: ссылки на стор в доке и README, раздел доки «Обновление» — после одобрения карточки (остаток issue #51).

## Capabilities

### New Capabilities

— нет.

### Modified Capabilities

- `runtime-hosts`: требование «Браузерное расширение» — постоянный ID расширения, общий для архива из релиза и версии
  из Chrome Web Store.

## Impact

- `src/extension/manifest.json` — поле `key`; `build.mjs` копирует manifest в `dist/extension/` как есть, поле
  попадает и в сборку `pnpm watch`.
- Новый тест в `tests/` — ID из ключа manifest.
- Версия — патч (0.14.2): поведение продукта не меняется, меняется идентичность установки из архива.
- Userscript не затронут.
