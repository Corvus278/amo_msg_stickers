## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь — то, что определяет подход.

- Отправка идёт штатным путём: `app.ts` в `toFile` превращает `SendItem` в `File` (`toGifFile` / `toCheckedGifFile`
  из `sender.ts`), `sendFile` вставляет его в поле ввода. Сейчас имена фиксированные: `sticker.gif` у стикера из
  пака, `gif.gif` у GIF из поиска.
- `SendItem` различает источник уже сейчас: `local` — стикер из IndexedDB (свой или из Telegram), `remote` — GIF из
  поиска. «Недавние» хранят тот же `SendItem`, поэтому вид повторной отправки не нужно запоминать отдельно.
- У `StickerRec` есть `emoji` (Telegram), подписи нет: `useStickerDraft` рисует её на кадрах и не сохраняет. У
  `RemoteGif` есть `title`; запроса поиска в `SendItem` нет.
- Наблюдаемое поведение amo (issue #21): имя файла доходит до получателя в `alt` картинки сообщения, GIF не
  перекодируется, хвост после последней точки сервер заменяет расширением по содержимому.
- Знание о DOM amo живёт только в `amoDom.ts`. Сборка — `target: chrome120`, `:has()` доступен.

## Goals / Non-Goals

**Goals:**

- Формат имени расширяем без поломки старых версий: новые параметры и порядок не ломают разбор.
- Стиль применяется к сообщениям, которые появятся в ленте позже, без слежения за DOM ленты.
- Правила не задевают сообщения без метки.

**Non-Goals:**

- Разные стили для стикеров и GIF, статичные стикеры в JPEG, обрезка прозрачных полей, увеличение стикеров меньше
  208 px — вне задачи (issue #21, «Вне задачи»).
- Стилизация уже отправленных `sticker.gif`.
- Юнит-тесты CSS и `app.ts`: они завязаны на DOM amo и проверяются стендом и живым amo (`testing.md`).

## Decisions

### Метка — в имени файла, стиль — CSS-селектором по `alt`

Имя — единственное, что отправитель задаёт и что сервер доставляет получателю как есть и кладёт в DOM. Селектор
по атрибуту работает без JS на каждое сообщение.

Альтернативы: метка в байтах GIF (Comment Extension) — пришлось бы скачивать и разбирать каждую картинку ленты из
`blob:`-URL и следить за лентой MutationObserver-ом; признак по размеру или пропорциям — ложные срабатывания на
обычных GIF.

### Модуль имени — `src/core/fileName.ts`

Чистые функции, типы — в `fileName.types.ts`:

- `buildStickerFileName({ kind, label, params })` → строка. `kind` — `'sticker' | 'gif'`, `params` — необязательные
  пары `ключ → значение` без `k`; расширение — `gif`, других форматов сейчас нет.
- Ключ и значение параметра — `[a-z0-9]`, ключ начинается с буквы: без точек и дефисов разбор однозначен. Невалидный
  параметр в `build` — ошибка программиста, `throw`: параметры приходят только из констант кода.
- `parseStickerFileName(name)` → `{ kind, label, params } | null`. Разбор по сегментам между точками:
  - последний сегмент — расширение (`[a-z0-9]+`); сегментов меньше трёх или расширения нет — `null`;
  - маркер `amostk` ищется сначала в сегменте 1 (тогда сегмент 0 — метка), затем в сегменте 0 (метки нет); иначе —
    `null`. Порядок проверки нужен для метки `amostk`: `amostk.amostk.k-gif.gif` — метка `amostk`, а не пропажа
    метки. Больше одного сегмента до маркера быть не может — точки из метки вычищены;
  - сегменты между маркером и расширением — параметры `ключ-значение`, разделитель — первый `-`. Сегмент не в этой
    форме пропускается: будущие версии формата могут добавить сегменты иного вида. Повтор ключа — действует первое
    вхождение;
  - вид — значение параметра `k`: `sticker` / `gif`, незнакомое значение или нет `k` — `kind: null`. Имя остаётся
    «нашим»: так же его видит CSS, который узнаёт своё по маркеру (`chat-message-style`), и будущий вид не
    превращает имя в чужое. `k` в `params` не попадает, незнакомые ключи — попадают;
  - `label` — пустая строка, если метки нет.
- `sendFileName(item, sticker)` — имя для отправки из `SendItem`: `local` → вид `sticker`, метка —
  `sticker.caption || sticker.emoji`; `remote` → вид `gif`, метка — `gif.title` (запись стикера не нужна). Вынесено
  из `app.ts` чистой функцией, чтобы выбор вида и метки, в том числе для «Недавних», покрывался тестом
  (`testing.md`).

Разбор в рантайме сейчас не нужен (узнаёт CSS), но он фиксирует формат тестами: сборка ↔ разбор, незнакомые
параметры, порядок.

### Вычистка и обрезка метки

`sanitizeLabel(raw)`, по шагам:

1. убрать `.`, `/`, управляющие символы `\p{Cc}` и bidi-символы U+202A–U+202E, U+2066–U+2069;
2. обрезать пробелы по краям;
3. набрать графемы (`Intl.Segmenter`) с начала, пока их не больше 32 и UTF-8 длина не больше 128 байт; графема
   целиком или не берётся;
4. снова обрезать пробелы по краям — обрезка могла оставить пробел в конце (`Привет .amostk.…`).

Пустой результат — метки нет.

- Графемы, а не UTF-16 единицы или кодпоинты: обрезка по единицам разрывает суррогатную пару и даёт `U+FFFD`, по
  кодпоинтам — рвёт ZWJ-эмодзи и флаги на куски.
- Потолок в байтах: длина графемы не ограничена (комбинирующие знаки), и 32 графемы могут дать тысячи байт; длинное
  имя сервер или браузер может урезать вместе с маркером. 128 байт вмещают 32 графемы кириллицы (64 байта) и 32
  простых эмодзи (128 байт); составные эмодзи урезаются раньше.
- Весь `\p{Cf}` не вычищается: в нём ZWJ U+200D, без которого составные эмодзи распадаются.
- Управляющие и bidi-символы, пробелы по краям и потолок в байтах — сверх issue: они не несут смысла в `alt`,
  перевод строки ломает скачивание, bidi-символы подменяют видимое имя скачанного файла.

### Откуда вид и метка

`app.ts` `toFile` берёт имя из `sendFileName` (см. «Модуль имени»). Вид следует из `SendItem.kind` — «Недавние»
получают правильный вид без изменения их записей. GIF из раздела
стикеров GIPHY — тоже `gif`: issue определяет `k-gif` как «GIF из поиска». Запрос поиска как метка не используется:
его нет в `SendItem`, и у «Недавних» он бы потерялся — `title` есть везде.

### Подпись своего стикера — поле `caption` в `StickerRec`

Необязательное `caption?: string | undefined`. В `useStickerDraft` два состояния подписи: сырое `caption` из поля
и `captionText` — обрезанное, после debounce, с ним идёт конвертация. Сохранять нужно ту подпись, с которой
нарисован готовый черновик: конвертация кладёт `captionText` в черновик рядом с GIF, `save` пишет её в `caption`.
Так подпись в записи совпадает с картинкой, даже если пользователь правит поле и жмёт «Сохранить» раньше, чем
пройдёт debounce. IndexedDB хранит значения structured clone-ом, схема хранилищ не меняется —
`DB_VERSION` остаётся 1. Стикеры, сохранённые раньше, подписи не имеют и уходят без метки.

Альтернатива — класть подпись в `emoji`: смешало бы смысл поля, а `stickerCellName` озвучивал бы подпись как эмодзи.

### `sender.ts` принимает готовое имя

`toGifFile(blob, fileName)` и `toCheckedGifFile(blob, fileName)` получают полное имя с расширением, без значения по
умолчанию: имя без метки не должно уйти молча.

### CSS — глобальный `<style>` из `amoDom.ts`

`amoDom.ts` экспортирует `injectMessageStyle()`: вставляет в `document.head` один `<style id="amo-stickers-message">`
(повторный вызов — no-op по `id`); `start()` зовёт её один раз. Текст CSS и селекторы ленты — константы там же.

- Область — только медиа сообщения в ленте. Картинка — `<путь медиа ленты> img[alt*="amostk."]`
  (`.media_wrapper_photo img…` или точнее по 4.1), пузырь — `<пузырь>:has(> <медиа ленты> img[alt*="amostk."])`
  с дочерним комбинатором. Голое `img[alt*="amostk."]` и `:has()` без пути не годятся: наша картинка с тем же
  `alt` бывает в цитате ответа, в пересланном сообщении, в просмотрщике медиа и в превью списка чатов — у текстового
  ответа пропал бы фон, просмотрщик получил бы лимит 208 px.
- Пузырь снимается только у сообщения, где кроме нашей картинки ничего нет: `:not(:has(<цитата>, <заголовок
  пересылки>, <подпись>))` по селекторам из 4.1. Ответ, пересылка и медиа с текстом остаются в пузыре и в прежнем
  размере: без фона их заголовок и цитата повисли бы в воздухе.
- Пузырь: у элемента пузыря — `background: none`, `box-shadow: none`, `border-radius: 0`; хвост (`svg` пузыря) и
  контейнер размытой подложки (`div` с `canvas`) — `display: none`. Оверлей времени и статуса не трогается.
- Размер стикера (`[alt*=".k-sticker."]`): картинка вписывается в 208×208, контейнер, который задаёт место под неё,
  повторяет размер картинки. Как именно — зависит от вёрстки, которую снимает 4.1:
  - `img` в потоке, контейнер с inline `width` / `height` → у контейнера `width` / `height: auto !important`,
    у картинки `max-width` / `max-height: 208px`, `width` / `height: auto`;
  - `img` — `absolute inset-0` поверх контейнера, размер задаёт контейнер → у картинки `position: static`,
    иначе контейнер с `auto` схлопнется в 0×0;
  - у контейнера `min-width` / `min-height`, `aspect-ratio` или `padding-top`-распорка → сброс (`0`, `auto`), иначе
    вокруг стикера останется пустая область;
  - `object-fit: contain` у картинки — всегда: при `object-cover` и неполном сбросе размеров стикер обрезался бы.

  `!important` — только против inline-стиля amo; HTML-атрибуты `width` / `height` перебиваются и без него.
  Константа `STICKER_MAX_SIDE_PX = 208`.
- Tailwind не используется: правила адресуют вёрстку amo, а не пикер, и живут вне shadow root.

Альтернатива — MutationObserver на ленту и классы на сообщения: лишняя работа на каждое сообщение, а CSS сам
применяется и к старым, и к новым узлам.

Точные селекторы пузыря, хвоста, подложки и контейнера размера подбираются в живом amo: часть классов — хэши
CSS-модулей, опора — стабильные tailwind-классы, структура и `alt`.

### Стенд

Мок «Отправить» в `dev/harness.html` строит разметку сообщения amo из issue (`div.container.is_outgoing` →
`div.message` с фоном, тенью и `svg`-хвостом → `.media_wrapper` → `button.photo_media_container` с `div > canvas`,
`img[alt=<имя файла>]` и оверлеем времени) вместо голой `<img>`. Переключатель «входящее» даёт `is_external`.
Стенд подключает тот же userscript — стиль приходит из `injectMessageStyle`.

Размер в моке задаётся так же, как в amo по итогам 4.1: лимит 420 px и способ, которым контейнер получает место
под картинку (inline-стиль, `absolute`-картинка, распорка). Правило стенда `#chat img { max-width: 200px }`
удаляется: с ним любая картинка уже меньше 208 px, и ни лимит стикера, ни «прежний размер» GIF не проверить. Для
проверки области — сообщение-ответ с цитатой нашей картинки: оно должно остаться в пузыре.

## Risks / Trade-offs

- [amo поменяет вёрстку ленты] → стиль молча перестанет действовать, сообщение покажется обычным пузырём — это
  безопасный исход. Селекторы — в одном файле, правка точечная.
- [Сервер исказит эмодзи или кириллицу в имени] → пострадает только метка для людей; маркер и вид — ASCII,
  стиль сохранится. Проверяется в живом amo с другого аккаунта.
- [`!important` против inline-стиля amo] → перебивает только у картинок с меткой; иначе размер контейнера не
  ограничить без JS.
- [Имя файла видно получателю при скачивании] → в имени только то, что и так видно: эмодзи, подпись, нарисованная
  на стикере, название GIF у провайдера.
- [Ложное совпадение: чужой файл с `amostk.` в имени] → получит стиль стикера; вероятность пренебрежима, вред —
  только вид.
- [Пересланный стикер и стикер-ответ остаются в пузыре и крупными] → сознательно: без фона заголовок пересылки и
  цитата повисли бы в воздухе. Вид таких сообщений — отдельное решение.
- [`<style>` в документе amo и CSP страницы] → `<style>` пикера уже живёт в shadow root на той же странице, но в
  документ amo не вставлялся; проверяется на 4.3 в живом amo.

## Migration Plan

Миграций нет: поле `caption` необязательное, версия IndexedDB прежняя. Откат — возврат версии; сообщения с меткой,
отправленные до отката, остаются обычными картинками с длинным `alt`.

## Open Questions

- Какой элемент ленты задаёт место под картинку и как: inline-стиль или атрибуты, `position` и `object-fit` у `img`,
  `min-*`, `aspect-ratio`, `padding` у контейнера — выясняется в живом amo (4.1). От ответа зависит, какой из
  вариантов раздела «CSS» применяется, а не подход.
- Селекторы цитаты ответа, заголовка пересылки, подписи к медиа, просмотрщика и превью в списке чатов — 4.1; от них
  зависит только `:not(:has(…))` и путь медиа ленты.
- Доходят ли эмодзи и кириллица в `alt` у получателя без искажений — проверка в живом amo; при искажении меняется
  только читаемость метки.
