## Context

Мотивация — proposal.md, «Why». Как и в change `send-via-amo-queue`, всё сказанное ниже об amo — наблюдаемое поведение
страницы и то, что видно в её бандле и рантайме (DevTools).

**Что сейчас.** Агент в мире страницы (`src/page/agent.ts`) по команде ядра находит `{ reduxStore, sendRequest }` amo,
собирает сообщение (`src/page/buildMessage.ts`) из открытого чата `state.location` и `state.dialogs` и кладёт его в
очередь запросом `sendNewMessages`. Ответ на сообщение агент не читает и в сообщение не кладёт — так требовала спека.

**Что видно в рантайме amo.**

- Активный ответ — запись черновика открытого чата `state.conversationDraughts[<id чата>]` с полем `refersTo` — id
  сообщения, на которое отвечают. Запись появляется по «Ответить»; без ответа её нет или `refersTo` пуст.
- Загруженные сообщения — `state.messages`, объект по id сообщения; у записи есть `id`, `conversationId`,
  `conversationType`, `flags` (флаги первым элементом массива) и `refersTo`.
- Сообщение очереди, которое страница собирает сама при ответе картинкой, несёт в поле `refersTo` объект сообщения, на
  которое отвечают, — у пересланного сообщения развёрнутый: содержимое исходного сообщения под `id`, чатом и адресатом
  пересланного, без флага пересылки (`128`).
- Кнопка «×» над полем снимает ответ запросом в ту же очередь: `sendRequest({ type:
  'updateConversationDraughtRefersToId', payload: { conversationId, refersToId: null } })`.
- Отправка из поля ввода (картинка, текст) уходит ответом и снимает плашку сама.

**Проверка в живом amo** (сниппет из DevTools, 2026-10-01, личный чат, React-провайдер на глубине 40): `refersTo`
черновика найден в redux сразу после «Ответить» (`id`, `refersTo`, `value`), сообщение — в `state.messages`.
Стикер 96×96 с объектом сообщения в `refersTo` ушёл через `sendNewMessages`; временное сообщение появилось в store
синхронно, уже с `refersTo`. Следом `updateConversationDraughtRefersToId` с `refersToId: null` снял плашку; оба запроса
вернули `undefined`. В ленте — стикер с цитатой, по цитате переход к сообщению работает; плашки нет; набранный текст
остался; после перезагрузки цитата на месте — её вернул сервер. Ответ на пересланное сообщение: флаг `128`, у записи
объект `refersTo`, разворот прошёл, сообщение принято. Без ответа — поведение #61. Групповой чат, GIF из поиска и
запасной путь с ответом не прогонялись — они в приёмке (tasks.md).

## Goals / Non-Goals

**Goals:**

- ответ читает и снимает агент: ядро и протокол агента не меняются;
- чтение ответа и сборка `refersTo` — чистые функции с юнит-тестами на форму состояния, включая пересланное и битое;
- снятие ответа не может привести ко второй отправке: после постановки стикера в очередь агент отвечает `accepted` при
  любом исходе снятия.

**Non-Goals:**

- ответ стикером на сообщение, которое страница не загрузила, — без подгрузки истории;
- слежение за исходом снятия ответа и повтор — показ плашки остаётся за amo.

## Decisions

### 1. Ответ читает агент, протокол не меняется

Агент берёт активный ответ из того же снимка `getState()`, из которого уже берёт чат: `state.conversationDraughts[<id
чата>].refersTo`. Ядро об ответе не знает: команда остаётся `{ id, op: 'send' }`, ответ — `accepted` или `rejected` с
прежними причинами. «Сообщения нет» — не отказ: стикер уходит без цитаты (п. 3), отказ увёл бы его на запасной путь.

- *Альтернатива — ядро читает плашку из DOM и передаёт id сообщения в команде*: отпадает — в DOM плашки id сообщения
  нет, а протоколу понадобилось бы новое поле, которое страница может подделать, ничего не выиграв.

### 2. `refersTo` сообщения — как у страницы

Новый модуль `src/page/refersTo.ts` — чистые функции рядом с гардом формы:

- `draughtReplyOf(state, conversationId, pendingClear)` — id ответа: `fieldOf` по цепочке `conversationDraughts →
  <id чата> → refersTo`, непустая строка; ответ, снятие которого ещё идёт, пропускается (п. 5);
- `quotedMessageOf(state, replyId)` — сообщение: `state.messages[<id ответа>]`, объект, у которого `id` совпадает с id
  ответа, а `conversationId` и `conversationType` — непустые строки (`isQuotedMessage` в `refersTo.types.ts`); иначе
  null. Пересланное (бит `128` в `flags[0]`) с объектом в `refersTo` разворачивается: поля вложенного сообщения,
  поверх — `id`, `conversationId`, `conversationType`, `toMember`, `to` пересланного и `flags: [flags[0] без 128]`.
  Пересланное без вложенного объекта уходит как есть — так цитирует его и страница. Неразвёрнутое сообщение идёт в
  `refersTo` тем же объектом из состояния, без копии: страница кладёт туда его же, а очередь меняет только само
  отправляемое сообщение;
- `attachReply(state, message, pendingClear)` — собранное сообщение стикера с `refersTo` при найденном ответе
  (`exactOptionalPropertyTypes`: без ответа поля нет), ответ к снятию (`replyToClear`) и что помнить агенту
  (`pendingClear`).

Объект целиком, а не `{ id, conversationId, conversationType }`: по этим трём полям сервер связывает ответ, а
остальное нужно временному сообщению, чтобы цитата была видна в ленте до ответа сервера. Тип — `AmoQuotedMessage` в
`refersTo.types.ts`: три проверенных поля и остальное как `unknown`.

`buildMessage` об ответе не знает и собирает стикер, как без него: ответ — отдельный шаг агента после сборки. Так
память агента не проходит через сигнатуру сборки сообщения.

- *Альтернатива — минимальный `refersTo` из трёх полей*: отпадает — временное сообщение показалось бы без цитаты до
  ответа сервера, и форма разошлась бы с той, что страница кладёт сама.

### 3. Сообщения ответа нет — без цитаты, ответ остаётся

Если `refersTo` черновика есть, а сообщения нет в `state.messages` или его форма не прошла проверку, стикер уходит без
цитаты и ответ не снимается: пользователь видит плашку и может ответить следующим сообщением. Это то, что требует
спека («Сообщение ответа не загружено»).

- *Альтернатива — отказ и запасной путь*: отпадает — при тексте в поле запасной путь остановит защита черновика, и
  стикер не уйдёт вовсе; при пустом поле результат зависел бы от того, что сделает отправка из поля.
- *Альтернатива — снять ответ и в этом случае*: отпадает — ответ пропал бы молча, без цитаты в отправленном.

### 4. Снятие ответа — после постановки в очередь, тем же запросом, что «×»

После того как `sendRequest` с `sendNewMessages` вернул промис без исключения и только если в сообщении есть
`refersTo` (`replyToClear` не null), агент вызывает `sendRequest({ type: 'updateConversationDraughtRefersToId', payload: { conversationId,
refersToId: null } })`. Оба вызова синхронные, поэтому ответ `accepted` по-прежнему уходит ядру внутри `dispatchEvent`.

- Исключение при вызове снятия — `console.warn`, ответ всё равно `accepted`: стикер уже в очереди, и `rejected` увёл бы
  ядро на запасной путь — второй стикер. Отказ промиса или `Error` в результате — `console.warn`, как у отправки
  (`logOutcome`). Плашка в этом случае остаётся — сценарий «Снятие ответа не удалось».
- Снятие после отправки, а не до: если бросит отправка, ответ остаётся в поле, и стикер уходит запасным путём ответом.
- Тем же запросом, что «×»: снятие идёт путём самой страницы со всем, что она при этом делает с черновиком. Прямая
  правка store (`dispatch`) обошла бы этот путь.
- *Альтернатива — не снимать ответ*: отпадает — issue #65 и спека требуют поведения картинки из поля.

### 5. Повторный клик до снятия ответа

Снятие ответа доходит до store не сразу (в живом amo запрос резолвился через ~300 мс), и стикер, отправленный в это
окно, прочитал бы тот же ответ и ушёл второй цитатой того же сообщения. Картинка из поля так себя не ведёт: после
отправки плашки нет, и следующее сообщение уходит без цитаты. Поэтому агент помнит снимаемый ответ — пару «id чата, id
сообщения» (`pendingClear`) — в замыкании `startAgent`:

- пока запрос снятия не завершился и черновик открытого чата показывает тот же ответ, стикер уходит без цитаты и без
  второго снятия;
- память сбрасывается, когда запрос снятия завершился — успешно или нет: после успеха плашки нет, и новый «Ответить»
  на то же сообщение — новый выбор пользователя; после неудачи плашка осталась, и следующий стикер, как картинка из
  поля, уходит ответом;
- память сбрасывается и раньше, если черновик уже показывает другой ответ или ответа нет: store догнал.

Сравнение со store — чистая функция рядом с чтением ответа (`src/page/refersTo.ts`), память и её сброс по исходу
запроса — у агента; оба проверяются юнит-тестами.

- *Альтернатива — блокировать повторный клик в ядре до резолва снятия*: отпадает — ядро не знает об ответе (п. 1), а
  ячейка и так не даёт второго стикера одним нажатием (`useCellSend`); второй клик — осознанный второй стикер.
- *Альтернатива — таймаут вместо сравнения со store*: отпадает — время снятия не гарантировано, а состояние store и
  есть то, что видит пользователь.

### 6. Запасной путь не меняется

`src/core/sender.ts` не трогается: вставка файла в поле и клик «Отправить» — штатная отправка страницы, а она уходит
ответом и снимает плашку сама, как с картинкой. Сценарий «Ответ на запасном пути» проверяется на стенде и в приёмке.

### 7. Модель угроз

Агент читает ответ из состояния страницы и снимает его запросом, который страница может послать и сама (`×`). В ответе
ядру ничего не прибавляется: ни id сообщения, ни признака ответа. Скрипт страницы, подменивший `refersTo` черновика,
получит стикер ответом на выбранное им сообщение — то же, что он может сделать, нажав «Ответить».

### 8. Стенд

`dev/harness.html`: поддельный store отдаёт `conversationDraughts` и `messages` из состояния стенда. Каждое сообщение
ленты стенда получает id и запись в `messages`. Кнопка «ответить» ставит ответ на последнее сообщение ленты — плашка
над полем с «×»; переключатель «сообщение ответа не загружено» убирает его из `messages`, переключатель «медленное снятие ответа» держит плашку ~1 с — для повторного клика. Поддельный `sendRequest`
понимает `updateConversationDraughtRefersToId` (снимает плашку) и кладёт `sendNewMessages` с `refersTo` в ленту
ответом с цитатой — тем же видом, что у кнопки «ответ с цитатой». «Отправить» на запасном пути тоже уходит ответом и
снимает плашку, как отправка из поля в amo. Цитата у обеих кнопок собирается одной функцией стенда.

### 9. Вид стикера-ответа — плашка цитаты рядом с картинкой, как в Telegram

Каркас DOM ответа в живом amo (2026-10-01, исходящий GIF-ответ): корень `[id^="message+"]` с `message_with_reply-` →
ряд → пузырь (`relative`) → первым ребёнком блок цитаты без класса CSS-модуля, за ним обёртка содержимого с медиа —
тот же путь до медиа, что у сообщения без ответа, — и панель действий (`absolute`, по верху сбоку от пузыря, внутри —
`message_controls-`). Поэтому стиль своего сообщения перестаёт исключать ответ на корне: пузырь, хвост, подложка и
размер снимаются теми же селекторами, что у стикера без ответа.

- **Плашка** — блок пузыря прямо перед обёрткой содержимого с нашим медиа (`div:has(+ div > <медиа>)`); строку автора
  на том же месте отсекает `:not(:has(> button))`. Плашка вынесена из потока (`position: absolute` от пузыря) в
  свободное место ряда: у исходящего — `right: calc(100% + …)`, у входящего — `left`. Картинка поэтому стоит ровно там,
  где стоял бы стикер без ответа, а высота сообщения не меняется. Верх и зазор отсчитаны от картинки: она сдвинута от
  края пузыря на `p-2` минус выход обёртки медиа (`-m-1`) — 4 px.
- **Цвет** — фон пузыря amo того же направления и темы: в DOM у пузыря классы `from-gray-110 to-white-0` /
  `dark:bg-black-60` у входящего и `from-flowerBlue-20 to-blue-120` / `dark:bg-beige-80` у исходящего. Значения —
  `src/core/bubbleTokens.ts` с ключом по пути токена: конфиг Tailwind в ядро не импортируется, а совпадение с
  `tailwind.config.ts` сверяет `tests/bubbleTokens.test.ts`. Цвета текста цитаты amo подобраны под этот фон. Направление — `is_outgoing-` на корне,
  тема — `dark` на `<html>`. Скругление и тень — `rounded-lgx` и `shadow-md` пузыря.
- **Ширина** — по содержимому (`max-content`), не больше 260 px и не больше свободного места рядом с картинкой: текст
  цитаты amo обрезает сам (`truncate`). Свободное место CSS знает через container query: ряд стикера-ответа — контейнер
  (`container-type: inline-size`), ширина плашки — в `cqw` от ряда. У стикера пузырь не шире стикера с отступами
  (208 + 8 px), и место рядом — `100cqw` минус пузырь; у GIF пузырь amo не шире 65% ряда, и рядом остаётся не меньше
  `35cqw`. Из места вычитаются зазор и слот чекбокса выбора (20 px), а у входящего под заголовком автора
  (`message_with_user-`) — ещё и аватар (46 px): у остальных сообщений аватара в ряду нет.
- **Узкий ряд** — когда плашка вышла бы уже 90 px, она встаёт над картинкой в потоке пузыря, шириной с картинку:
  `width: 0` не даёт ей растянуть пузырь, `min-width` растягивает по картинке, которая выходит за отступ пузыря на
  4 px с каждой стороны (`calc(100% + 8px)` и отрицательные боковые `margin`). Порог ряда считается из тех же констант
  для каждого случая: стикер и GIF — 332 px, под заголовком автора — 378 и 463 px. Так у Telegram-вида нет обрезанной
  краем ленты плашки.
- **Клик** — штатный переход amo по цитате. Плашка поднята над зоной наведения пузыря (`::after` поверх соседнего
  места ряда) и панелью действий (`z-20`): иначе клик ушёл бы им.
- **Панель действий** у стикера-ответа опущена к низу пузыря: по верху её место заняла плашка.

- *Альтернатива — плашка в потоке пузыря (над картинкой или сбоку flex-рядом с переносом)*: отпадает — проверено в
  живом amo, выглядит криво: плашка сдвигает картинку с её места у края ленты, а у маленького стикера плашка шире
  него.
- *Альтернатива — только убрать размытую подложку, оставив пузырь с цитатой*: отпадает — Telegram-вид согласован как
  целевой.
- *Альтернатива — цвета плашки через `background: inherit` от пузыря*: отпадает — фон пузыря тогда пришлось бы прятать
  трюком (`background-clip: text`), который наследуется вместе с фоном; явные токены проще проверить.

## Risks / Trade-offs

- [amo переименует `conversationDraughts`, `messages` или поле `refersTo`] → ответ не найден, стикер уходит без
  цитаты, плашка остаётся; отправка не ломается. Покрыто тестами на форму состояния.
- [amo сменит запрос снятия ответа] → стикер уходит ответом, плашка остаётся, в консоли — предупреждение.
- [amo сменит форму `refersTo` так, что сервер не свяжет ответ] → после перезагрузки стикер без цитаты; видно сразу,
  лечится выпуском. Приёмка — перезагрузка после отправки.
- [запрос снятия резолвился раньше, чем store показал «нет ответа»] → стикер в это окно ушёл бы второй цитатой того же
  сообщения. Проверено в живом amo (2026-10-01, три замера сниппетом из DevTools): к резолву запроса
  `updateConversationDraughtRefersToId` черновик в store уже без ответа — окна нет.
- [amo сменит цвета пузыря] → плашка разойдётся по цвету с пузырём, раскладка не сломается; правка — токены в
  `tailwind.config.ts` и `bubbleTokens.ts`, тест не даст поправить одно без другого.
- [amo сменит разметку цитаты] → без совпадения селектора цитата остаётся в потоке без фона над стикером без пузыря.
  Приёмка — стикер-ответ в обеих темах и обоих направлениях.
- [amo сменит лимит ширины пузыря, отступы ряда или размер аватара] → оценка места рядом с картинкой разойдётся, и
  плашка в узком окне может снова упереться в край ленты. Приёмка — сужение окна до перехода в узкий режим.
- [ответ в одном чате, отправка — в другом] → не возникает: черновик читается по id открытого чата.

## Migration Plan

Миграции данных нет. Откат — выпуск предыдущей версии: стикер снова уходит без цитаты.
