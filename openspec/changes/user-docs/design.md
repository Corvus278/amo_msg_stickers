## Context

Мотивация — proposal.md, требования — specs/. Что есть сейчас:

- Инструкция по установке — раздел README для разработчика. Каталога `docs/` и Pages нет.
- Заголовок userscript собирается строками в `build.mjs` (`USERSCRIPT_BANNER`); `isWatch` уже разделяет боевую и
  dev-сборку (адреса localhost). `tests/userscriptBanner.test.ts` проверяет заголовок по сырому тексту `build.mjs`.
- Архив расширения называется `amo-stickers-<версия>.zip` в `ci.yml` (артефакт PR) и `release.yml` (файл релиза).
- Подсказки со ссылками собирает `renderMessage` из строк словаря `messages.{ru,en}.ts` с подстановкой `{link}`;
  компонент ссылки `ExternalLink` лежит в `SettingsView/` и используется только там.
- `*.md` исключены из prettier, `docs/` не входит в `PRODUCT_PATHS` — правка только доки не требует подъёма версии.
  Корневые `package.json` и `pnpm-lock.yaml` в `PRODUCT_PATHS` входят целиком.
- Корневой `pnpm-workspace.yaml` держит только настройки (`allowBuilds`), пакетов workspace нет.
- Официально userscript проверяется только в Tampermonkey; Violentmonkey и другие менеджеры с тем же GM API работают
  без гарантий.

## Goals / Non-Goals

**Goals:**

- Сайт доки, который собирается и проверяется так же строго, как код: битая ссылка ломает PR.
- Адрес доки и страниц, на которые ссылается интерфейс, — одно место в ядре, с проверкой, что страницы существуют.
- Текст доки пишется и читается в Markdown; разметка сайта в нём — минимальная.
- Движок доки обновляется без подъёма версии продукта.

**Non-Goals:**

- Английская дока (#54), публикация в сторах (#51), свой домен для доки.
- Своя тема VitePress: тема по умолчанию, расширенная только компонентом вкладок плагина, без своих компонентов и
  стилей.
- Скрины: места отмечены, файлы добавит автор.
- Гарантии для Violentmonkey и Safari: дока описывает их установку, но они не проверяются.

## Decisions

### Дока — отдельный пакет в `docs/` со своим lockfile

`docs/` — самостоятельный проект pnpm: свои `package.json` (`vitepress`, `vitepress-plugin-tabs`),
`pnpm-workspace.yaml` и `pnpm-lock.yaml`. Собственный `pnpm-workspace.yaml` делает `docs/` корнем своего workspace:
pnpm ищет ближайший файл workspace вверх по дереву, поэтому корневой не подхватывает `docs/`, а корневой
`pnpm-lock.yaml` зависимостей доки не содержит. В `docs/pnpm-workspace.yaml` — свой `allowBuilds` (esbuild для Vite).
Поведение pnpm с вложенным workspace сверяется при установке (tasks 1.1): корневой `pnpm i` не меняет корневой
lockfile, `pnpm -C docs i` ставит зависимости доки.

Корневой `package.json` получает только скрипты: `docs:dev` / `docs:build` / `docs:preview` — `pnpm -C docs …`.
`typecheck` проверяет оба проекта: корневой `tsconfig.json` и `docs/tsconfig.json`.

Почему не корневые devDependencies: `package.json` и `pnpm-lock.yaml` — файлы продукта, и каждое обновление VitePress
требовало бы подъёма версии и выпускало релиз без изменений в продукте. Почему не пакет общего workspace: lockfile у
workspace один, корневой — и он тоже файл продукта. Сужать `PRODUCT_PATHS` до секций lockfile — сложнее и хрупче, чем
отдельный lockfile.

Цена — вторая установка: `.github/actions/setup` ставит зависимости корня и доки (`pnpm -C docs install
--frozen-lockfile`), ключ кэша стора считается по обоим lockfile. Ставят все задания CI: eslint и `typecheck` проверяют
конфиг доки и без её зависимостей упали бы на импорте `vitepress`.

Альтернатива MkDocs — второй стек (Python) в CI.

### Конфиг VitePress

`docs/.vitepress/config.mts`: `base: '/amo_msg_stickers/'`, `lang: 'ru-RU'`, `cleanUrls`, локальный поиск,
`srcDir: 'content'` (страницы отдельно от пакета и конфига, статика — `docs/public/` через `vite.publicDir`), `locales`
с одним `root` (русский) — английский встанет в `/en/` без смены русских адресов. Битые внутренние ссылки VitePress по
умолчанию считает ошибкой сборки — это и есть проверка ссылок, `ignoreDeadLinks` не трогаем. `srcExclude` — общие
фрагменты (`_parts/**`, «Структура страниц»): иначе VitePress собрал бы каждый фрагмент отдельной страницей, со своим
адресом и в поиске.

Конфиг и тема — TypeScript, `docs/tsconfig.json` их включает; eslint находит его через `projectService` и проверяет
файлы доки по общим правилам. Кэш и сборка VitePress (`docs/.vitepress/cache`, `docs/.vitepress/dist`) — в
`.gitignore`, `.prettierignore` и `ignores` eslint наравне с `dist`: это сгенерированные файлы, а не послабление правил.

### Вкладки установки — `vitepress-plugin-tabs`

Синтаксис `:::tabs` / `== Название` в Markdown. Плагину нужны две точки подключения: `tabsMarkdownPlugin` в
`markdown.config` конфига и компонент вкладок в теме — `docs/.vitepress/theme/index.ts` расширяет тему по умолчанию
и зовёт `enhanceAppWithTabs(app)`. Больше в теме ничего нет. На GitHub сырой md покажет разметку вкладок текстом —
принято: читают сайт. Перед подключением сверить, что плагин поддерживает установленную версию VitePress; если нет —
вкладки заменяются разделами на одной странице (вариант, отклонённый при обсуждении, как запасной), и файл темы не
нужен.

### Места под скрины — HTML-комментарии

`<!-- скрин: img/<раздел>/<имя>.png — что на нём -->`. Картинку `![](...)` на несуществующий файл VitePress не соберёт:
Vite разрешает её при сборке. Комментарий в сайт не попадает, а автор находит все места поиском по `скрин:`. Скрины
лежат в `docs/content/img/<раздел>/` и подключаются относительным путём от страницы.

### Структура страниц

```
docs/content/
  index.md                 главная: что это, возможности, кнопка «Установить» -> install/
  install/index.md         выбор окружения: Chromium, Firefox, Safari, десктоп
  install/chromium.md      вкладки: Chrome Web Store | Архив | Userscript
  install/firefox.md       userscript: Tampermonkey; Violentmonkey — без гарантий
  install/safari.md        Userscripts — без гарантий
  install/desktop.md       пока недоступно
  setup/gif-keys.md        KLIPY, затем GIPHY; лимиты тестовых ключей
  setup/telegram.md        @BotFather -> токен -> ссылка на пак -> импорт
  update.md
  faq.md
  privacy.md
  _parts/userscript.md     общие шаги userscript (в srcExclude, не страница)
```

Выбор окружения — одно место, `install/index.md`: главная ведёт на него кнопкой, пункт «Установка» сайдбара — тоже.

Userscript описан на `install/chromium.md` вкладкой и отдельно на `install/firefox.md` и `install/safari.md` — повтор
шагов менеджера выносится в `_parts/userscript.md` и подключается `<!--@include: ...-->` VitePress, чтобы текст не
расходился.

### Менеджеры userscript

Основной путь — Tampermonkey: только он проверяется. Violentmonkey и Safari (приложение Userscripts) описаны короче, с
пометкой «без гарантий»: способ может работать, но не проверяется. Для Safari отдельно сказано, что без хранилища
менеджера настройки лежат в `localStorage` amo — как у скрипта без менеджера (`runtime-hosts`, «Настройки»): даёт ли
Userscripts синхронные `GM_getValue` / `GM_setValue`, при написании доки не проверяется.

### Адрес доки в ядре — `src/core/userDocs.ts`

Базовый адрес и страницы, на которые ссылается интерфейс (`gif-keys`, `telegram`), — константы одного модуля; функция
собирает полный адрес страницы. Язык не параметр: до #54 все ссылки ведут на русскую доку. Тест проверяет, что для
каждой страницы модуля есть `docs/content/<страница>.md`, — переименование страницы доки без правки ядра ломает тест, а не
ссылку у пользователя.

Имя `userDocs`, а не `docs`: в корне проекта `docs/` — исходники сайта, одноимённый модуль ядра путал бы поиск.

### Подсказки в интерфейсе

- `ExternalLink` переезжает из `SettingsView/` в общий `Picker/ExternalLink/`: ссылки появляются ещё в `GifView/` и
  `AddView/TelegramImport/`.
- Ссылка на доку — отдельная подстановка `{docs}` в строке подсказки со своим текстом ссылки из словаря, как `{link}`:
  порядок слов вокруг неё задаёт перевод. Английский текст ссылки говорит, что инструкция на русском («instructions
  (in Russian)»): до #54 английской доки нет, и пользователь не должен ждать английскую страницу.
- Настройки: порядок полей KLIPY → GIPHY → токен; у KLIPY `{link}` на `https://partner.klipy.com/api-keys`.
- Режим «GIF» без ключей: под «Открыть настройки» — ссылка на `setup/gif-keys`.
- Импорт: к нынешней подсказке — какие стикеры конвертируются в GIF — добавляется, где в Telegram взять ссылку на пак,
  и ссылка на `setup/telegram`. Точный путь по меню Telegram сверяется с приложением при написании доки и
  подставляется в словарь тем же текстом.

### Автообновление userscript

В `USERSCRIPT_BANNER` — `@updateURL` и `@downloadURL` на
`https://github.com/Corvus278/amo_msg_stickers/releases/latest/download/amo-stickers.user.js`, добавляются так же, как
`devMatches`: только при `!isWatch`. `latest` — всегда наибольшая версия: это уже обеспечивает `release.yml`.

Отдельный `.meta.js` не выпускаем. Менеджер сравнивает `@version` из файла по `@updateURL` с установленной; без
`.meta.js` на каждую проверку он скачивает весь userscript (сотни килобайт). Проверки редкие (Tampermonkey — раз в
сутки по умолчанию), а второй файл в каждом релизе и его сборка того не стоят.

Тест — в `tests/userscriptBanner.test.ts` по сырому `build.mjs`: обе директивы есть, адреса совпадают с ожидаемым.
Отсутствие в `watch` проверяется руками по `dist/amo-stickers.user.js` после `pnpm watch`. Само обновление в менеджере
проверяется только следующим релизом («Migration Plan»).

### Постоянное имя архива

`ci.yml` собирает `dist/amo-stickers.zip`, `release.yml` прикладывает его под тем же именем. Прямая ссылка доки —
`releases/latest/download/amo-stickers.zip`. Версия видна в теге релиза и в `chrome://extensions`.

Обновление архива в доке: удалить содержимое папки расширения, распаковать новый архив в ту же папку и нажать
«Обновить» в `chrome://extensions`. Распаковка поверх без очистки оставила бы файлы, удалённые в новой версии. Папка —
та же, потому что ID распакованного расширения зависит от пути, а с ID — хранилище ключей и токена.

Альтернативы: два файла в релизе (с версией и без) — дубль в каждом релизе; ссылка на страницу релиза — лишний шаг и
выбор файла для не-программиста.

### Публикация — `pages.yml`, проверка — задание в `ci.yml`

- `ci.yml`: шестое задание `docs` — `pnpm docs:build`. Релиз гоняет `ci.yml` целиком, поэтому битая дока в `master`
  не даст и релиза — приемлемо: в `master` она попасть не может, её ловит PR.
- `pages.yml`: `push` в `master` с `paths` (`docs/**`, `.github/actions/setup/**`, `.mise.toml`, корневой
  `package.json` — в нём скрипт `docs:build`, сам workflow) и `workflow_dispatch`; сборка через
  `./.github/actions/setup`, `actions/upload-pages-artifact`, `actions/deploy-pages`;
  `permissions: pages: write, id-token: write`; `concurrency` группы `pages` без отмены идущего. Не в `release.yml`: правка текста не должна ждать релиза и подъёма версии.
- До мержа `pages.yml` не запустить: `workflow_dispatch` доступен только для workflow из default branch, а окружение
  `github-pages` по умолчанию принимает деплой только из `master`. Сборку, которую публикует `pages.yml`, в PR
  проверяет задание `docs` той же командой; деплой проверяется первым мержем («Migration Plan»). Отдельный
  `pull_request`-триггер в `pages.yml` дублировал бы задание `docs`.

### README

Сверху — для пользователя: заголовок и одна фраза, демо (место под GIF), возможности, кнопка «Установить» на доку,
ссылки «скачать архив» и «установить userscript» на последний релиз. Ниже — «Разработка»: сборка, проверки, стенд
короче нынешнего, со ссылкой на CLAUDE.md для устройства. Таблица «Что проверено» и «Дальше» уходят: первая устарела,
вторая живёт в issue.

### Тексты

Тексты доки, README и новых строк словаря проходят скилл `typograf` (неразрывные пробелы, кавычки, тире). В строки
словаря и Markdown идут символы Unicode (неразрывный пробел, «», —), а не HTML-сущности: `&nbsp;` в строке словаря
Preact покажет текстом.

## Risks / Trade-offs

- [Pages не включён в настройках репозитория — первый деплой упадёт] → разовое ручное действие автора (Settings →
  Pages → Source: GitHub Actions), отдельной задачей в tasks.md до мержа.
- [`vitepress-plugin-tabs` отстал от VitePress] → проверить совместимость при установке; запасной вариант — разделы
  на странице.
- [Вложенный `pnpm-workspace.yaml` pnpm обработает не так, как ожидается, и корневой lockfile получит зависимости
  доки] → сверяется в tasks 1.1 по `git diff pnpm-lock.yaml`; запасной вариант — флаг `--ignore-workspace` в командах
  доки; не помогает и он — вопрос автору до продолжения.
- [Вторая установка зависимостей в каждом задании CI] → стор pnpm кэшируется по обоим lockfile; VitePress ставится
  секунды из кэша.
- [Пути меню Telegram, название переключателя Tampermonkey, шаги Opera/Edge для Chrome Web Store меняются от версии к
  версии] → сверяются при написании; в доке — формулировки без номеров версий, где можно.
- [Лимит тестового ключа KLIPY не сверен] → цифра берётся из Partner Panel при написании `setup/gif-keys.md`; для
  GIPHY — 100 запросов в час у бета-ключа.
- [Violentmonkey и Safari не проверяются] → пометка «без гарантий» в доке; в FAQ — что делать, если не работает
  (Tampermonkey или расширение).
- [Смена имени архива ломает старые прямые ссылки на `amo-stickers-<версия>.zip`] → внешних ссылок нет; старые
  релизы не меняются.
- [Вкладка «Chrome Web Store» до одобрения #51 ведёт в никуда] → до публикации вкладка говорит «на проверке» и ведёт к
  архиву и userscript; ссылку на стор ставит #51.

## Migration Plan

1. Мерж PR: релиз с `amo-stickers.zip` и userscript с `@updateURL` выходит сам.
2. Pages включён заранее — `pages.yml` публикует доку тем же мержем. Проверка после мержа: прогон `pages.yml`
   зелёный, `https://corvus278.github.io/amo_msg_stickers/` открывается, ссылки из пикера ведут на существующие
   страницы.
3. Уже установленный userscript без `@updateURL` менеджер не обновит: один раз поставить новую версию по ссылке из
   доки, дальше — сам. Об этом — в разделе «Обновление».
4. Проверка автообновления — со следующим релизом: Tampermonkey с userscript этого релиза по «Проверить обновления»
   находит и ставит новую версию.

Откат: revert PR; сайт Pages остаётся до следующего деплоя или отключается в настройках.
