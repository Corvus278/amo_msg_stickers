# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

amo stickers — стикеры и GIF для мессенджера amo (web). В строке ввода рядом с кнопкой эмодзи появляется
кнопка стикеров, наведение или клик открывает попап с двумя режимами. «Стикеры» — одна лента недавних, своих
стикеров из картинки, GIF, видео или `.tgs` с подписью и паков, импортированных из Telegram. «GIF» — поиск GIPHY и
KLIPY и недавние GIF. Стикер отправляется кликом.

Публичного API для отправки сообщений у amo нет, поэтому код живёт внутри чужой страницы и отправляет стикер
внутренней очередью amo — той же, которой amo отправляет опрос, — отдельным сообщением, не трогая поле ввода. Если
очередь недоступна, стикер уходит штатным путём пользователя: вставкой файла в поле ввода и кликом «Отправить».

Дока пользователя — сайт VitePress из `docs/` на GitHub Pages, `https://mcar2107.github.io/amo_msg_stickers/`:
установка по браузерам, ключи GIF, импорт из Telegram, обновление, частые вопросы, политика конфиденциальности —
на русском (корень сайта) и английском (`/en/`). README — вход в неё: сверху описание, «Установить» и ссылка на
английскую инструкцию, разработка ниже.

## Стек и сборка

TypeScript (strict) + esbuild. UI пикера — Preact (JSX с `jsxImportSource: 'preact'`, классы по варианту и состоянию
описывает `cva` из `class-variance-authority`), стили — Tailwind 3 с токенами amo в `tailwind.config.ts`: цвета, шрифты,
тени и шкала отступов совпадают с tailwind-классами страницы amo, поэтому класс из её вёрстки значит в пикере то же
самое. GIF кодирует `gifenc` — потоково, в Web Worker-е, `.tgs` рендерит `lottie-web` (light canvas-плеер: без
`eval`, который не пропускает CSP расширения). Пакетный менеджер — pnpm, версии Node и pnpm — в `.mise.toml`.

```bash
pnpm i
pnpm build             # dist/extension/* и dist/amo-stickers.user.js
pnpm watch             # пересборка при изменениях, с inline-sourcemap и адресами localhost:3000
pnpm typecheck         # только проверка типов (TS 7): корень и конфиг доки (docs/tsconfig.json)
pnpm lint              # eslint + typecheck + prettier --check параллельно
pnpm lint:fix          # eslint --fix
pnpm format            # prettier --write
pnpm test              # vitest, проект `unit`
pnpm skills:update     # openspec update: перегенерация .claude/skills/openspec-* и .claude/commands/opsx
pnpm -C docs i         # зависимости доки — отдельный пакет со своим lockfile
pnpm docs:dev          # сайт доки локально; docs:build — сборка (падает на битой ссылке), docs:preview — её показ
```

Одно ядро (`src/core`) собирается в две цели (`build.mjs`, формат IIFE, `target: chrome120`):

- **расширение** Chrome / Яндекс / Edge (MV3): content script + service worker, `dist/extension/`;
- **userscript** для Tampermonkey и других менеджеров: `dist/amo-stickers.user.js` с заголовком `==UserScript==`.

У сборки три esbuild-плагина: `tailwind` отдаёт ядру CSS пикера строкой, `gif-worker` — код Worker-а кодирования GIF,
`page-agent` — код агента в мире страницы для userscript («Сборка CSS и Worker-а»).

Различия целей спрятаны за интерфейсом `Host` (`core/host.types.ts`): сеть и хранение настроек. Расширение ходит в
сеть через service worker — обход CORS, настройки держит в `chrome.storage.local`. Userscript с менеджером ходит в
сеть через `GM_xmlhttpRequest` — тоже в обход CORS и без cookie целевых сайтов, настройки держит в хранилище
менеджера (`GM_getValue` / `GM_setValue`), недоступном странице. Без менеджера (скрипт подключён на страницу
напрямую) — прямой `fetch` со страницы под её CORS и `localStorage`. Заголовок userscript просит гранты этих `GM_*`,
`@connect` к хостам сетевой политики и изолированный мир (`@sandbox DOM`, `@inject-into content`).

Боевая сборка запускается только на `https://*.amo.tm/*`; `http://localhost:3000/*` и `http://127.0.0.1:3000/*`
`build.mjs` добавляет в manifest и в заголовок userscript лишь в `pnpm watch`. Заголовок боевой сборки несёт
`@updateURL` и `@downloadURL` на userscript последнего релиза (`releases/latest/download/amo-stickers.user.js`) —
менеджер обновляет скрипт сам; в `pnpm watch` их нет, иначе менеджер заменил бы dev-сборку версией из релиза.

TypeScript в проекте двух версий: `typescript-native` (7.x, нативный tsgo) проверяет типы, `typescript` (6.x) нужен
только typescript-eslint, который TS 7 пока не поддерживает. `node_modules/.bin/tsc` занят одной из них — проверку
типов запускай через `pnpm typecheck`.

Дока — отдельный пакет pnpm в `docs/` со своим `package.json` и `pnpm-lock.yaml` (`vitepress` и
`vitepress-plugin-tabs` точными версиями; override `@types/markdown-it` в `docs/pnpm-workspace.yaml` сводит типы
VitePress и плагина): зависимости сайта не попадают в lockfile расширения. Корневые `docs:*` — это `pnpm -C docs …`.
После клона и перед первым коммитом нужен `pnpm -C docs i`: pre-commit гоняет `pnpm typecheck`, а он проверяет и
`docs/tsconfig.json`. Конфиг — `docs/.vitepress/config.mts`: `base: '/amo_msg_stickers/'`, `cleanUrls` (адрес
страницы — база и путь исходника без `.md`), страницы — в `docs/content/` (`srcDir`), статика — в
`docs/public/` (`vite.publicDir`); фрагменты `docs/content/_parts/` подключаются `<!--@include: …-->` и сами
страницами не собираются (`srcExclude`).

Языков доки два (`locales` в `config.mts`): русский — корень, английский — локаль `en` (`lang: 'en-US'`,
`link: '/en/'`) в `docs/content/en/`, который зеркалит пути русских страниц, поэтому переключатель языка ведёт на ту
же страницу другой локали. Английский фрагмент — `docs/content/_parts/en/`. Меню, сайдбар и служебные подписи темы
(`outline`, `docFooter`, `skipToContentLabel`, `notFound` и прочие) — свои у каждой локали, пункт сайдбара называется
как H1 его страницы; локальный поиск строит индекс на локаль, и английская страница находит только английские.
Английские страницы берут те же файлы из `docs/content/img/` на уровень глубже (`../img/` → `../../img/`, `./img/` →
`../img/`), без копий; `alt` — по-английски, скрины — с русским интерфейсом, оговорка об этом одна, на
`en/index.md`. Названия экранов и кнопок amo stickers в английском тексте — строки `messages.en.ts`. `CopyCode`
выбирает подписи по ключу локали страницы (`localeIndex`): `en` — «Copy» / «Copied», иначе русские.

**Правило: правка страницы доки — в обоих языках одним PR.** Пары страниц сверяет `tests/userDocsPages.test.ts`
(пути через `import.meta.glob`): страница без пары на другом языке роняет тест.

Цвета и шрифт — как у пикера: `docs/.vitepress/theme/style.css`
переопределяет переменные VitePress значениями токенов `tailwind.config.ts` (синий акцент в светлой теме, бежевый —
в тёмной). Логотип — `docs/public/logo-{light,dark}.svg` (шапка и иконка вкладки по теме системы) и
`logo-hero-{light,dark}.svg` (главная). Способы установки — вкладки `::::tabs`. Скрины и демо — в
`docs/content/img/<раздел>/` (PNG через `pngquant`, личные данные размыты; узкий кадр — `<img>` с `width`), видео на
главной — WebM и MP4, в README — GIF. Место под скрин, которого ещё нет, — комментарий
`<!-- скрин: img/<раздел>/<имя>.png — что на нём -->`, а не картинка на несуществующий файл: её Vite не соберёт.
Адрес `chrome://extensions` и подобные — компонент темы `<CopyCode>` (`theme/CopyCode.vue`): браузер не пускает на
такие адреса по ссылке, и адрес копируется по клику.
Тексты доки и строк словаря проходят typograf символами Unicode (неразрывный пробел, «», —), без HTML-сущностей;
английские — с локалью `en-US`. Страницу доки typograf проходит по тексту, а не файлом целиком: целиком он ломает
markdown (`- ` списков, `::::tabs`, `../` путей), а неразрывные пробелы, которые он ставит внутри code-span,
после прогона убираются.

## Как работает

### Встраивание в amo

`start(host)` в `core/app.ts` запускается один раз на страницу (флаг `window.__amoStickers`). MutationObserver на
`body` (с группировкой в `requestAnimationFrame`) ищет поля ввода и вставляет кнопку сразу после обёртки эмодзи.
Классы обёртки и иконки повторяют родную кнопку эмодзи — tailwind-стили amo применяются к ней без своего CSS, а
цвет иконки открытого/закрытого пикера переключается заменой классов: базовый `fill` заменяется, а не дополняется,
иначе из двух `fill-*` победит тот, что позже в CSS amo.

Попап один на страницу, у каждого поля ввода — своя кнопка. Когда и у какой кнопки его открыть, решает контроллер без
DOM `createHoverPopup` (`core/hoverPopup.ts`), `app.ts` только переводит в него события курсора:

- **Наведение.** Курсор над кнопкой дольше 250 мс открывает попап, уход с кнопки и попапа закрывает его через 500 мс;
  возврат до конца задержки закрытие отменяет. Уход курсора за окно (`mouseout` без `relatedTarget`) — тоже уход.
- **Клик** закрепляет попап, в том числе уже открытый наведением: уход курсора его не закрывает, и наведение на кнопку
  другого поля ввода не переносит — переносит только клик. Клик по кнопке закреплённого попапа закрывает его, а клик
  вне попапа, Escape и отправка закрывают попап при любом способе открытия.
- **Удержание.** Открытый наведением попап не закрывается уходом курсора, пока есть причина удержания
  (`hoverPopupHolds.ts`): фокус в текстовом поле панели, открытый диалог выбора файла, идущий импорт пака, идущая
  конвертация стикера, открытый предпросмотр. Удержание спрашивается в момент срабатывания таймера закрытия, а снятие
  последней причины при курсоре снаружи запускает закрытие.
- **Уход.** Закрытая панель 200 мс уходит анимацией (`hoverPopupPhase.ts`) и не принимает курсор; возврат курсора к
  той же кнопке в это время открывает её сразу, из текущего положения перехода.

`data-testid` в amo нет: селекторы в `amoDom.ts` держатся за aria-атрибуты (`aria-placeholder`,
`aria-label="Send message"`, `aria-label="cancel edit"`) и стабильные tailwind-классы. Знание о DOM amo живёт только
в этом файле — при правке вёрстки amo меняется он один.

### Пикер

Пикер — Shadow DOM, его хост вставляется внутрь кнопки: `position: fixed` считается от предка с transform —
контейнера поля ввода, как у родного попапа эмодзи. Shadow root отрезает CSS amo от пикера и CSS пикера от amo:
preflight Tailwind не сбрасывает вёрстку страницы. Корень — `closed`: на экране «Настройки» лежат ключи GIF и токен
бота, и через `element.shadowRoot` скрипт страницы до них не доберётся.

`app.ts` живёт в DOM amo без Preact и управляет пикером через фасад
`createPicker(host, { onSend, onClose, onHoldRelease })`: `open(openedBy)`, `close()`, `setTheme(isDark)`,
`isHeld()`, признаки `isOpen` и `isClosing`. Фасад перерисовывает дерево `render()` на каждое изменение, а закрытый
пикер остаётся смонтированным — режим, прокрутка лент и запрос поиска переживают повторное открытие. Данные и
действия (настройки, паки, статус, отправка, удержание, импорт из Telegram) компоненты берут из `usePicker()`
провайдера `PickerProvider`, режим, экран и якорь ленты стикеров — из `usePickerView()`. Занятость отправки живёт в
ячейке (`useCellSend`): повторное нажатие на ту же ячейку не уходит вторым стикером, соседние остаются доступны, а
занятая ячейка — `disabled` с индикатором поверх картинки (`CellSpinner/`).

**Режимы и экраны.** Внизу панели — футер (`Footer/`): переключатель режимов «Стикеры» и «GIF» и кнопка «Настройки».
Оба режима смонтированы всегда (`ModePanel/`), неактивный скрыт `display: none`: запрос поиска и загруженная выдача
переживают переключение, а прокрутку, которую скрытие сбрасывает, панель запоминает и возвращает при показе.
Выбранный режим пишется в `localStorage` страницы (`pickerMode.ts`) и открывается в следующий раз, в том числе после
перезагрузки; без сохранённого режима или при сбое чтения открывается «Стикеры», если в библиотеке есть стикер, иначе
«GIF» (`usePickerView/startMode.ts`). Экраны «Добавить стикеры» и «Настройки» (`Screen/`) лежат оверлеем поверх
режима: режим под ними `inert` и остаётся в раскладке, поэтому «Назад» возвращает в тот же режим с той же прокруткой
и запросом поиска.

**Движение.** Появление — переход из `[@starting-style]:` при показе: панель режима проявляется после `display: none`
(`ModePanel/`), строка статуса — при появлении плашки (`StatusBar/`), меню — только после замера места (вариант
`isPlaced` в `Menu/`), поэтому не мигает в углу. Экран появляется прозрачностью и сдвигом на 8 px анимацией скрипта
(`element.animate()` в `Screen/`) при монтировании, `key={screen}` проигрывает и смену экрана на экран: переход из
`@starting-style` проигрался бы заново при каждом открытии попапа — закрытая панель скрыта `display: none`, а экран
остаётся смонтированным. «Назад» проигрывает ту же анимацию обратно, с текущего места и вдвое быстрее — за 100 мс от
показанного экрана, — и закрывает экран по её концу: режим под экраном `inert`, пока экран не закрыт, и ввод в ленту
возвращается только тогда. Повторное «Назад» во время ухода ничего не делает, а экран, снятый во время ухода кнопкой
футера, закрытием его анимации не задевается. `display: none` закрытой панели анимацию скрипта не отменяет: уход,
начатый перед закрытием попапа, доигрывается, и экран закрывается по его концу; закрытие по отмене анимации — только
защита. Меню закрывается сразу. Прозрачность и сдвиг не трогают раскладку, и элемент принимает ввод с первого кадра.
Кнопки, чипы источников GIF и зона загрузки меняют вид при наведении (`Button/`, `FeedChip/`, `DropZone/`), вкладки,
кнопки футера, «+» и плитка — переходом цвета. Наведение кнопок — через вариант `enabled:`: недоступная кнопка его не
получает, «Импорт» недоступна при пустой ссылке.

Уменьшение движения в системе выключает всё это одним вариантом: переход пишется только под `motion-safe:`, а стартовое
состояние `[@starting-style]:` — без варианта, и без перехода оно не видно. Длительность — тоже под `motion-safe:`
(`motion-safe:duration-base`, `motion-safe:duration-lg`): `motion-safe:transition-*` несёт свою длительность по
умолчанию в `@media`-блоке, который идёт позже простого `duration-*` и перебивает его. Анимация экрана и прокрутка
читают настройку в `scrollMotion/`: `isMotionReduced()` — экран появляется и закрывается сразу, `scrollMotion()` —
`'auto'`, мгновенно, иначе `'smooth'`; настройка читается на каждый переход, без подписки. Спиннер отправки крутится и
при уменьшении движения.

**Режим «Стикеры»** (`StickersMode/`) — полоса вкладок разделов (`SectionTabs/`) над одной лентой всех разделов
(`StickerFeed/`): недавние стикеры, «Мои стикеры», паки из Telegram. На вкладке раздела пака — статичный первый кадр
стикера-обложки на `<canvas>` (`PackCover/`). Экран «Добавить стикеры» открывают кнопка «+» справа от полосы
(`AddButton/`) — она не вкладка, лежит вне `tablist` и не прокручивается с вкладками, — и плитка «Создать стикер» в
конце «Моих стикеров» (`StickerFeed/CreateTile/`): лишний слот раздела `custom` (`hasCreateTile` в `stickerLayout/`),
в том числе в пустом разделе, без контекстного меню и отправки. Выбранной считается раздел в верху видимой области.

Переход к разделу — `scrollToSection(sectionId, motion)`: якорь в `usePickerView` несёт способ прокрутки. Вкладка просит
`'smooth'`: лента едет плавно, а к разделу дальше высоты видимой области сначала мгновенно встаёт на экран от него
(`sectionScrollPlan/`) — иначе окно рядов провело бы через документ все промежуточные паки. Окно рядов в точке этого
перехода готовится до него: ряды монтируются рядом с текущим окном, их картинки декодируются (`decodeFeedImages/`,
потолок ожидания 120 мс), и только потом лента прыгает — иначе после прыжка она несколько кадров стоит пустой, пока
декодер догоняет экран. Поэтому у картинок ячеек нет `loading="lazy"`: ленивая картинка далеко за видимой областью не
грузится, и декодировать заранее было бы нечего. Пока лента едет, запас рядов держится только по ходу движения
(`feedWindowRanges/`), а выбранной остаётся нажатая вкладка (`scrollLock/`: удержание снимается через 150 мс без событий
прокрутки), а не разделы, мимо которых идёт прокрутка. Колесо, касание, нажатие и клавиша на ленте снимают удержание,
отменяют ещё не сделанный прыжок и обрывают доезд: Chrome не обрывает программную плавную прокрутку вводом. Касание,
нажатие и клавиша останавливают ленту мгновенной прокруткой на месте. Первый шаг колеса лента отменяет и делает сама —
`scrollTo` от текущей прокрутки на сдвиг колеса в пикселях (`wheelDeltaPx/`: строки и страницы пересчитываются), плавно,
как родное колесо, а при уменьшении движения — сразу: Chrome вливает колесо в ещё живую программную прокрутку, и
остановка на месте съела бы шаг. Колесо с Ctrl (масштаб) не отменяется и останавливает ленту на месте, следующие шаги
колеса прокручивают ленту нативно. Сохранение своего стикера и импорт пака просят `'instant'` — раздел ставится одним
шагом.

Полоса держит выбранную вкладку по центру своей видимой части (`useCenterTab/`, края — по границам прокрутки), а
подложка и черта выбранной вкладки — один элемент на полосу (`tabIndicator/`), который переезжает к новой вкладке.
Пока полоса видна, она доезжает плавно, при показе (открытие попапа, возврат в «Стикеры») полоса и индикатор сразу
стоят на месте. Постановку запускают смена выбранной и смена набора вкладок: новый раздел сдвигает выбранную без
смены раздела. Индикатор ставится мгновенно выключением перехода на одно синхронное чтение `offsetWidth`, а не до
следующего кадра: `requestAnimationFrame` из обработчика вне кадра сработал бы до отрисовки.

**Режим «GIF»** (`GifView/`) — поиск, переключатель источников (GIPHY GIF, GIPHY стикеры, KLIPY — те, для которых
есть ключ) и лента в две колонки (`MasonryGrid/`) в порядке выдачи: без запроса — недавние GIF и под ними «Тренды»,
с запросом — только результаты. Следующая страница подгружается за 200 px до низа ленты, на время загрузки в конце
колонок стоят заглушки. Открытие кликом в режиме «GIF» и переключение в него кликом ставят фокус в поиск, открытие
наведением фокус из поля сообщения не забирает.

**Виртуализация.** Обе ленты держат в документе только видимую область и запас по её высоте сверху и снизу (лента
стикеров на плавном переходе к разделу — только по ходу движения): стикеры и GIF за пределами окна не декодируются и не
проигрываются. Исключение — окно рядов в точке прыжка к далёкому разделу: его картинки декодируются до прыжка, пока оно
ещё за экраном («Переход к разделу» выше). Геометрия считается заранее, до загрузки картинок: у стикеров — ряды по 5
ячеек и заголовки разделов 32 px (`stickerLayout/`), у GIF — пиксельные позиции плиток, каждая следующая встаёт в самую
короткую колонку (`MasonryGrid/splitColumns/`). Размеры лент снимает `ResizeObserver`. Вход в ленту по Tab встаёт на
первый видимый целиком элемент, по Shift+Tab — на последний, без прокрутки (`useFeedEntry/`): первый по порядку Tab
элемент лежит в запасе над видимой областью, и браузер прокрутил бы ленту к нему.

**Меню.** Удаление живёт только в меню (`Menu/`): кнопки на ячейках заслоняли бы сетку. Контекстное меню ячейки
открывают правый клик, клавиша меню и `Shift+F10` — своей проверкой: Chrome на macOS по `Shift+F10` не шлёт
`contextmenu`. Меню есть у каждой ячейки стикера и у каждой GIF, включая тренды и результаты поиска; первый пункт
всегда «Предпросмотр». У найденной GIF он единственный, у стикера из библиотеки следом идёт «Удалить стикер», у
недавних стикеров и GIF — «Убрать из недавних» (состав пунктов — `cellMenuItems`).
У заголовка пака — кнопка «…» с «Удалить пак», у заголовка недавних (обоих видов) — «Очистить», у «Моих стикеров»
действий нет. Удаление пака и очистка недавних подтверждаются повторным нажатием за 2,5 с (`useConfirmPress`), а не
`confirm()`: модальные диалоги браузера блокируют страницу amo. Меню закрывают Escape и Tab с возвратом фокуса на
источник, клик вне меню и прокрутка.

**Предпросмотр** (`Preview/`) показывает стикер или GIF крупно поверх области режима — над лентой, вкладками и экранами,
под строкой статуса и футером: картинка вписана с сохранением пропорций и увеличивает мелкую, анимация играет. У GIF
это версия для отправки, а до её загрузки — превью ленты, растянутое на то же место. Он один на панель, а не на ячейку:
ячейки лежат под виртуализацией и размонтируются, оверлей и отпускание кнопки должны их пережить. Открывается двумя
способами.

- **Удержание.** Основная кнопка мыши или пера на ячейке дольше `HOLD_DELAY_MS` (300 мс) — жест `createPressGesture`, на
  ячейке его подключает `usePressPreview`; сдвиг курсора больше `HOLD_SLOP_PX` (6 px) или уход с ячейки отменяют его,
  правая и средняя кнопки не участвуют, Ctrl+клик (правый клик на macOS) тоже, касание тоже (`HOLD_POINTER_TYPES`: у
  касания длинное нажатие открывает меню браузера, а его пункт ведёт в тот же предпросмотр), занятая отправкой ячейка
  не открывает. Оверлей не принимает курсор (`pointer-events-none`), фокус не переносится, скринридеру предпросмотр
  удержания не объявляется. Отпускание (`pointerup`, `pointercancel`) закрывает предпросмотр где бы ни оказался курсор
  — слушатели висят на `window` и взводятся синхронно в `openHold` провайдера, а не эффектом после рендера:
  отпускание в пределах кадра после срабатывания задержки иначе проскочило бы. Ближайший `click` после отпускания
  гасится в capture-фазе (слушатель снят по `setTimeout(0)`), поэтому удержанная ячейка ничего не отправляет. Ячейка
  флага «держали» не хранит.
- **Меню.** Пункт «Предпросмотр» (`openPinned`) открывает закреплённый предпросмотр: диалог с фокусом на кнопке «Закрыть
  предпросмотр». Закрывают Escape (только предпросмотр, попап остаётся), клик в любом месте области — он не доходит до
  ленты и ничего не отправляет, эта кнопка и уход фокуса за пределы; также переключение режима, экран и закрытие
  попапа. После закрытия Escape, кликом или кнопкой фокус возвращается на ячейку, если она ещё в ленте; после ухода
  фокуса — нет.

Пока предпросмотр открыт, живёт причина удержания `preview` (`PANEL_REASONS` в `hoverPopupHolds.ts`): попап, открытый
наведением, не закрывается уходом курсора. Причину пишет только провайдер, `setHold('preview', открыт)`. Появление —
прозрачностью за 175 мс (`duration-base`) под `motion-safe:`, закрытие сразу. Имя диалога — целая фраза словаря из
`cellName/` («Предпросмотр стикера «привет»»).

Фокус после удаления не падает в `body` (`useRemovalFocus/`, цели — `removalFocus/`): в ленте стикеров он встаёт на
соседнюю ячейку раздела (следующую, иначе предыдущую), в опустевшем разделе — на его вкладку, а после удаления раздела
целиком («Удалить пак», «Очистить») — на вкладку соседнего; в ленте GIF — на соседнюю недавнюю GIF, иначе в поле поиска, без ключей — на
«Открыть настройки». Фокус переводится, если он потерян или остался в пикере — на узле, который Preact отдал соседнему
разделу, — и не забирается, если пользователь успел уйти из пикера, например в поле ввода amo.

Панель — `<dialog>` с `aria-label`. Переключатель режимов и полоса разделов — паттерн ARIA tabs: в порядке Tab стоит
только выбранная вкладка, стрелки, `Home` и `End` переводят фокус (`moveTabFocus/`), выбирает Enter, пробел или клик.
Режим лежит в своём `tabpanel` с `aria-labelledby` кнопки режима, лента стикеров — в `tabpanel` вкладки активного
раздела. Строка статуса — постоянная live region (`role="status"`) слоем поверх низа ленты: лента не меняет высоту,
когда статус появляется. Кольцо фокуса — только по `:focus-visible` (`@layer base` в `picker.css`). Кнопки ячеек
называются по `cellName/` целыми фразами словаря: «Отправить стикер 😀», у своего стикера с подписью — «Отправить
стикер «привет»», «Отправить GIF «cat»»; на английском — «Send sticker “привет”»: подпись не переводится.

Тема следует за классом `dark` на `<html>`: `app.ts` следит за ним MutationObserver-ом и зовёт `setTheme`, корень
пикера получает класс `dark`, а `dark:`-варианты Tailwind (`darkMode: 'selector'`) срабатывают внутри shadow root.
Цвета в компонентах — только токены из `tailwind.config.ts`, без hex-литералов и inline-цветов.

### Язык интерфейса

Интерфейс — на русском или английском, как у amo web (`core/i18n/`). Язык выбирается первой строкой `start()` —
`setLocale(readAmoLocale())` — и до перезагрузки страницы не меняется, поэтому он состояние модуля `translate.ts` без
подписок. Источник — язык, который amo сохранил в `localStorage` страницы под ключом `i18nextLng`
(`AMO_LOCALE_KEY`); без значения или при сбое хранилища — первый из `navigator.languages` (пустой список —
`navigator.language`). Основной тег `en` без учёта регистра и региона даёт английский, любой другой язык и его
отсутствие — русский, запасной язык amo (`resolveLocale` — чистая функция). Код вне `start()` — тесты, service
worker расширения — получает русский без настройки. Выбор «язык amo» на стенде пишет тот же ключ.

**Словари.** `messages.ru.ts` (`RU`) — эталон: из него выводятся тип ключа `MessageKey` и имена подстановок `{name}`
каждой строки. `EN` типизирован `Record<MessageKey, string>` — ключ без перевода или лишний ключ не компилируется.
`t(key, params)` требует параметры только у строки с подстановками, и вызов без нужной подстановки не компилируется;
подстановка без значения остаётся в тексте как есть — пропуск виден в интерфейсе. Ключи сгруппированы префиксами по
месту: `picker.` `footer.` `screen.` `add.` `settings.` `stickers.` `pack.` `cell.` `menu.` `gifs.` `status.`
`error.`. Строку, внутри которой стоит элемент — ссылка в подсказке настроек, — собирает `renderMessage/`: фраза
остаётся одним ключом, порядок слов вокруг ссылки задаёт перевод, а на месте подстановки встаёт узел Preact.
Библиотеки i18n нет: два языка без множественных форм — зависимость в бандле content script и userscript не
окупается. Строка, зависящая от числа, получит `Intl.PluralRules` в том же модуле.

**Где зовётся `t`.** В рендере и в момент броска ошибки, а не в константах модуля: модули вычисляются до
`setLocale` в `start()`, и константа застыла бы на русском. Поэтому таблицы подписей держат ключи
(`Record<…, MessageKey>`), а текст берётся `t` при показе.

**Ошибки.** Ошибки ядра в мире страницы — `new Error(t(…))` / `new SendError(t(…))` на текущем языке. Service
worker языка amo не знает: `localStorage` страницы ему недоступен. Поэтому ошибки, которые создаёт и SW, и мир
страницы — политика хостов и лимит размера из `core/net.ts`, — `LocalizedError`: `Error` с ключом и параметрами
рядом с текстом. Граница SW — `src/extension/fetchResponse.ts`: `toFailureResponse` в `background.ts` кладёт в отказ
`key` и `params` только у `LocalizedError`, `unwrapFetchResponse` в `content.ts` пересоздаёт по ним `LocalizedError`
на языке amo, если ключ есть в словаре и параметры совпадают с подстановками его строки; иначе — `Error` с текстом SW
как есть. Адаптер `gmNetwork` userscript работает в мире страницы и переводит свои ошибки сети, таймаута и обрыва
`t` при броске. Параметры ошибки — HTTP-статус, начало тела, лимит в мегабайтах — сохраняются.

**Что не переводится.** Данные пользователя: подписи своих стикеров, названия паков Telegram, названия и запросы
GIF. Технические тексты без перевода — `HTTP <код> <тело>`, сообщения браузера, `fetch failed` отказа без ответа SW,
описание отказа от Bot API (`description`) — показываются как есть. Атрибуция «Powered by GIPHY / KLIPY» и подписи «GIPHY API key»,
«KLIPY API key» — одинаковые на обоих языках. Логи консоли и ошибки-инварианты, которые видит только разработчик
(«Неизвестный формат ответа» в SW, недостижимые ветки `switch`, невалидный параметр имени файла, хук вне своего
провайдера), не переводятся. Имя отправляемого файла от
языка не зависит: маркер и вид не переводятся, метка — данные пользователя («Имя файла и стиль в ленте»), и
стикер, отправленный при одном языке, у собеседника с другим языком — стикер.

**Свой пак.** Его название берётся `packTitle(pack)` (`ui/Picker/packTitle/`) по id `custom` — `t('pack.custom')`,
«Мои стикеры» или «My stickers», — а не из записи: `title` в IndexedDB остаётся на языке, при котором пак создан, и
переписывать его ради подписи значило бы мигрировать базу при каждой смене языка. Название пака Telegram — данные
пользователя, `packTitle` отдаёт его как есть. Любой показ названия пака — вкладка, заголовок раздела, буквы обложки,
статус «Пак добавлен» — идёт через `packTitle`.

**Язык выдачи GIF.** Функции `sources/gifs.ts` принимают `locale` последним аргументом, `useGifFeed` передаёт
`getLocale()` на каждый запрос. GIPHY получает `lang` только в поиске (у трендов параметра нет), KLIPY —
`locale=ru_RU` или `en_US` в поиске и в трендах.

**Ссылки на доку.** Подсказки настроек, режима «GIF» и импорта из Telegram ведут на страницу доки на языке
интерфейса: адрес считается в рендере — `userDocsUrl(page, getLocale())`, как `t`, а не константой модуля.
Префиксы языков — `Record<Locale, string>` в `userDocs.ts` (`ru` — корень сайта, `en` — `en/`): язык интерфейса без
префикса своей доки не компилируется.

**Метаданные сборок.** Описание расширения — `__MSG_extDescription__` в `manifest.json` из
`src/extension/_locales/{ru,en}/messages.json`, `default_locale` — `ru`: браузер с языком без перевода показывает
русское описание. `build.mjs` копирует `_locales` в `dist/extension/` при старте сборки — в `pnpm watch` правка
`messages.json` не перекопируется до перезапуска. Заголовок userscript несёт `@description` на русском и
`@description:en`; название «amo stickers» одно на оба языка. Иконки — `src/extension/icons/` (`icons` в
`manifest.json`, `build.mjs` копирует их так же, как `_locales`); у userscript `@icon` — та же иконка 48 px, встроенная
data URI: менеджеру не нужно ходить за ней в сеть. Кнопка расширения (`action`) меняет иконку по теме браузера
(`actionIcon.ts`): тему видит только страница (`prefers-color-scheme`), поэтому content script шлёт service worker-у
сообщение `amo-stickers:icon-theme` при старте и при смене темы, а тот зовёт `chrome.action.setIcon` — тёмные иконки
лежат в `icons/dark/`. До первого сообщения, в том числе без открытой вкладки amo, стоит светлая `default_icon`.

**Правило: строки интерфейса — только через словарь.** Любой текст, который пользователь видит или слышит, — подпись,
плейсхолдер, `aria-label`, `title`, статус, текст ошибки — заводится ключом парой в `RU` и `EN` и показывается через
`t` или `renderMessage`, а не литералом в компоненте, хуке или модуле ядра. Названия, у которых в amo есть свой
перевод («Отправить», «Настройки», «Поиск», «Удалить»), совпадают с ним на обоих языках. Тест, который переключает
язык `setLocale('en')`, возвращает `'ru'` в `afterEach`. Проверка охвата — поиск кириллицы вне комментариев в `src/`:
она остаётся только в `messages.ru.ts`, `_locales/ru/` и русских ошибках-инвариантах из исключений выше.

### Сборка CSS и Worker-а

`picker.css` собирает esbuild-плагин `tailwind` в `build.mjs`: PostCSS с Tailwind по конфигу из `tailwind.config.ts`, в
сборке — минификация (в `watch` CSS остаётся читаемым), и в бандл CSS попадает строкой (loader `text`,
`declare module '*.css'` в `src/types.d.ts`). Фасад кладёт её `<style>` в shadow root. Tailwind ищет классы в
`src/core/ui/**/*.tsx`; конфиг и компоненты плагин отдаёт в `watchFiles`, поэтому `pnpm watch` пересобирает CSS при их
правке.

Код отдельного бандла строкой отдаёт фабрика esbuild-плагинов `bundleCodePlugin` в `build.mjs`: модуль `<имя>:code`
экспортирует строку с IIFE-бандлом входа. Ею собраны два модуля — `gif-worker:code` и `page-agent:code`
(`PAGE_AGENT_CODE`, агент в мире страницы из `src/page/index.ts`: его userscript вставляет элементом `<script>`).
Расширению агент нужен файлом — `dist/extension/page.js`, отдельная точка входа того же `src/page/index.ts`.

Код Worker-а кодирования GIF собирает плагин `gif-worker`: `src/core/gifWorkerEntry.ts` — отдельным бандлом
(IIFE, в сборке минифицирован, в `watch` — с inline-sourcemap), который попадает в ядро строкой из виртуального модуля
`gif-worker:code` (`GIF_WORKER_CODE`, `declare module` в `src/types.d.ts`). Строкой — потому что userscript не может
подключить отдельный файл Worker-а, и ядро запускает его из blob URL. Код Worker-а лежит в `content.js` и в
userscript; `background.js` конвертацию не импортирует, и строки в нём нет. Входы бандла Worker-а плагин отдаёт в
`watchFiles` — правка кодировщика в `pnpm watch` пересобирает и код Worker-а внутри ядра.

Vitest плагина не знает, поэтому `gif-worker:code` в тестах не грузится: его импортирует только `workerSink.ts`, а
тесты проверяют клиент Worker-а (`workerSinkClient.ts`) и протокол (`gifWorker.ts`) без него. `convert.ts` и
`frameSink.ts` тесты не импортируют напрямую, а тест модуля, который тянет `convert.ts` транзитивно
(`telegram.test.ts` через `sources/telegram.ts`), обязан подменить его `vi.mock` — иначе импорт упрётся в
`gif-worker:code`.

### Отправка

```
blob → File(image/gif, имя из sendFileName) → sendFile
  ├─ очередь amo: команда агенту → sendRequest({ type: 'sendNewMessages' }) → accepted
  └─ запасной путь: paste в contenteditable → вложение → click [aria-label="Send message"]
```

Основной путь — очередь отправки amo, та же, которой уходит опрос: стикер идёт отдельным сообщением, поле ввода
(текст, вложения, ответ, редактирование, курсор) не трогается. Очередь видна только скриптам страницы, поэтому
отправляет агент в мире страницы (`src/page/`): ядро помечает поле ввода и скрытый `<input type="file">` с файлом
атрибутом с `id` команды и шлёт `CustomEvent` (`shared/pageBridge.ts`, клиент — `core/pageClient.ts`); `<input>` лежит
в `documentElement`, а не в `body`, чтобы не будить `MutationObserver` ядра и amo. Агент находит
`{ reduxStore, sendRequest }` amo по fiber от поля ввода (`findClient.ts`), собирает сообщение так же, как страница
кладёт в очередь опрос (`buildMessage.ts`: чат — из `state.location` и `state.dialogs`, фото с `localFlag:
PREPARING`, без ответа), вызывает `sendRequest` и отвечает синхронно: `accepted` или `rejected` с причиной. Пометки и
`<input>` клиент снимает сразу по ответу.

Выбирает путь `sendFile` (`sender.ts`): `accepted` — готово; `rejected` или нет ответа к возврату из `dispatchEvent`
(агента нет) — `console.info` с причиной и сразу запасной путь, без ожидания. После `accepted` запасного пути нет при любом исходе загрузки: один клик — одно сообщение.
Исход загрузки ядро не ждёт — неудачу amo показывает в ленте неотправленным сообщением с «Повторить», — поэтому
«отправлено» значит «amo принял»: для очереди — `accepted`, для вставки — клик «Отправить»; после этого `app.ts`
пишет недавние. `media.id` сообщения совпадает с `localPhotoSize.localFileId`, как у своих вложений amo: иначе amo
не найдёт файл при загрузке и повторе.

Запасной путь — вставка файла в поле ввода. В `DataTransfer` кладётся **только** файл: при наличии `text/plain` поле вставит текст, а не
вложение. Вложение ждём до 15 с по появлению кнопки «Отправить». Если в поле есть текст или вложения, либо идёт
редактирование, отправка блокируется `SendError` — иначе стикер ушёл бы вместе с черновиком.

Имя файла собирает `app.ts` через `sendFileName` и передаёт в `toGifFile` / `toCheckedGifFile` готовым: имени по
умолчанию у `sender.ts` нет.

GIF из поиска (и из недавних GIF) тяжелее 2 МБ (`MAX_GIF_BYTES`) пережимается штатной конвертацией: `app.ts`
скачивает выбранную версию, проверяет байты `toCheckedGifFile` и отдаёт файл `toStickerGif(file, 'image')`
(«Конвертация»: сторона до 512 px, анимация до 4 с и 100 кадров, лестница сторон до 2 МБ). На последней стороне
лестницы результат уходит как есть, даже тяжелее 2 МБ, — как свой стикер. Решение — по весу скачанного файла, а не по
весу из выдачи: так пережимается и GIF из выдачи без весов, и недавняя GIF со ссылкой на тяжёлую версию. Проверка GIF —
до конвертации: страница ошибки получит «Файл не похож на GIF», а не ошибку декодера. Файл до 2 МБ уходит без
изменений.

### Имя файла и стиль в ленте

amo показывает имя отправленного файла `alt`-ом картинки в ленте — по нему CSS узнаёт сообщение amo stickers.

- **Имя** (`fileName.ts`) — `[метка.]amostk.k-<вид>[.<ключ>-<значение>]*.gif`. Вид — `sticker` (стикер из пака) или
  `gif` (GIF из поиска, в том числе из недавних GIF). Метка — для людей: у стикера подпись своего стикера, без неё —
  эмодзи; у GIF — название. Метку вычищает и ограничивает по длине `sanitizeLabel`; пустая не пишется, и имя
  начинается с маркера. `parseStickerFileName` разбирает имя симметрично сборке.
- **Стиль** — один глобальный `<style id="amo-stickers-message">` в `document.head` из `injectMessageStyle()`
  (`amoDom.ts`); `start()` зовёт его до первого поиска полей ввода, повторный вызов ничего не делает. CSS сам
  применяется к сообщениям, которые появятся в ленте позже, без слежения за её DOM.
- **Селекторы.** `img[alt*="amostk."]` — наше сообщение, `[alt*=".k-sticker."]` — стикер. Классы CSS-модулей amo —
  `<имя>-<хэш>`, хэш меняется от сборки к сборке, поэтому селекторы держатся за основу `[class*="<имя>-"]`, корень
  сообщения `[id^="message+"]` и путь корень → ряд → пузырь → обёртка содержимого → медиа ленты. Та же картинка в
  цитате ответа, пересылке, просмотрщике и превью лежит по другому пути и не задевается.
- **Что меняется.** У нашего сообщения нет пузыря, хвоста и размытой подложки, а под заголовком автора (групповой
  чат, канал) скрыта и строка имени, аватар остаётся. Стикер — не больше 208 px по стороне (`STICKER_MAX_SIDE_PX`, как
  у стикеров Telegram): место под картинку и минимальный размер кнопки сбрасываются.
- **Что остаётся в пузыре:** ответ с цитатой, пересылка, медиа с подписью или реакциями. Сообщения, отправленные
  с именем без маркера (`sticker.gif`), не меняются.

### Конвертация

amo перекодирует PNG и WebP в JPEG с белым фоном, без изменений проходит только GIF — поэтому любой источник
приводится к GIF с 1-битной прозрачностью (`convert.ts`). Конвертация потоковая: в памяти не больше двух несжатых
кадров в очереди Worker-а плюс кадр на холсте, а кодирование идёт в Web Worker-е, не занимая главный поток страницы.

```
источник → план кадров → кадр на холст прохода (+ подпись) → getImageData → приёмник (Worker | главный поток) → GIF
```

- **Источник кадров** (`openFrameSource`, `frameSource*.ts`) — план (позиция и задержка кадра) и отрисовка кадра по
  номеру; размер вписан в 512 px, мелкий источник не увеличивается. Картинки — `ImageDecoder` (план строится
  декодированием каждого кадра с немедленным `close`) с фолбэком на `createImageBitmap`; видео — покадровым seek
  одного `<video>`; `.tgs` — Lottie на своём холсте, в холст прохода кадр переносится `drawImage`. Источник служит
  всем проходам и освобождается в `dispose` при любом исходе: у видео снимается `src`, зовётся `load()` и
  отзывается blob URL — иначе декодер и файл держатся до сборки мусора и выгрузки страницы.
- **Анимация** — до 100 кадров и 4 с, 25 fps (40 мс — ровно 4 сотых: у GIF задержка в сотых); у анимированной
  картинки — её собственные задержки, кадр, выходящий за 4 с, урезается до их конца (не ниже 20 мс), одиночный кадр
  даёт статичный GIF.
- **Выбор стороны** (`sidePick.ts`, `encodeLadder.ts`) — ряд: сторона источника, затем меньшие неё из 384 / 320 /
  256 px. Если план длиннее 8 кадров (`SAMPLE_FRAMES`) и сторона источника больше 256 px (ряду есть куда уменьшаться),
  сначала пробный проход: 8 кадров равномерно по плану в размере источника; иначе старт — сторона источника. Вес пробы
  масштабируется на весь план и по площади на каждую сторону ряда, с запасом `SAFETY`. Старт по пробе — наибольшая
  сторона, чья оценка не больше 2 МБ (`MAX_GIF_BYTES`, одна константа на весь код). GIF тяжелее лимита кодируется заново
  следующей стороной ряда — новым проходом по источнику; на последней стороне результат отдаётся как есть. Подпись
  рисуется на холсте прохода, в том числе в пробе, — текст не мылится от даунскейла.
- **Кодировщик** (`gifEncoder.ts`, без DOM) — кадр индексируется и сжимается сразу при записи. Палитра строится в
  rgb565 только по непрозрачным пикселям, прозрачность — отдельный индекс; упорядоченный дизеринг Байера 4×4
  включается, если средняя ошибка цвета без него выше порога: узор привязан к координатам и не мерцает в анимации.
- **Приёмник кадров** (`createFrameSink`, свой на каждый проход) — кодирует в Worker-е из blob URL (`workerSink.ts`,
  `workerSinkClient.ts`). Кадр уходит Worker-у transfer-ом, без копии; без `ack` в полёте до двух кадров (окно 2):
  захват следующего кадра идёт, пока Worker кодирует предыдущий, но не обгоняет кодирование больше чем на кадр.
  `byteLength` отстаёт на кадры в полёте, поэтому проба читает вес после `flush` — когда `ack` пришёл на каждый её
  кадр. Worker живёт один проход: `close` останавливает его, и память кодировщика уходит вместе с ним.
- **Фолбэк** (`frameSinkMain.ts`) — тот же кодировщик на главном потоке, поток уступается странице после каждого кадра.
  Включается, если Worker не заработал до первого `ack` (CSP, исключение конструктора): первый кадр уходит Worker-у
  копией и повторяется в фолбэке, в консоль — `console.warn`. После такого сбоя фабрика (`createFallbackAwareSink`) до
  перезагрузки страницы сразу отдаёт фолбэк, без повторного запуска Worker-а. Сбой Worker-а после первого `ack` и его
  сообщение `error` — ошибка конвертации: кадры не кодируются второй раз на главном потоке. Основной путь — Worker:
  он снимает кодирование с главного потока, и страница amo не подвисает на время конвертации. Фолбэк в скрытой
  вкладке медленнее: браузер тормозит `setTimeout`, которым он уступает поток, а через 5 минут в фоне Chrome включает
  intensive throttling — цепочки таймеров просыпаются примерно раз в минуту.
- GIF без подписи и в пределах 2 МБ проходит как есть.

### Окружения и адаптеры

Ядро знает только контракты `core/host.types.ts`: `HostNetwork` (`fetchJson`, `fetchBlob`) и `HostSettings`
(`getSettings`, `setSettings`), `Host = { name } & HostNetwork & HostSettings`. Окружение собирает `Host` из своих
адаптеров и передаёт в `start(host)`; импорт из `src/userscript/` и `src/extension/` ядру запрещает eslint
(«Линтинг»).

Второй контракт с окружением — агент в мире страницы (`src/page/`, протокол — `shared/pageBridge.ts`, «Отправка»):
окружение подключает его само до `start`. Расширение — content script `page.js` с `"world": "MAIN"` в manifest:
своим файлом, без вставки кода в страницу. Userscript — `injectPageAgent` (`src/userscript/pageAgent.ts`): строка
`PAGE_AGENT_CODE` элементом `<script>`, который удаляется сразу после вставки; так же и без менеджера. Не подключил —
ядро не получит ответа агента, и отправка пойдёт запасным путём. Повторное подключение (расширение и userscript на
одной странице) агент гасит флагом `window.__amoStickersPage`.

Адаптеры userscript — чистые функции, зависимости приходят параметрами, поэтому тесты гоняют их без менеджера:
`gmNetwork(request)`, `fetchNetwork()`, `gmSettings(gmStore, storage)`, `localStorageSettings(storage)`. Режим
выбирается в одном месте — `src/userscript/index.ts`: `GM_*` менеджер кладёт в область видимости скрипта, а не в
`window`, поэтому проверка — `typeof GM_xmlhttpRequest === 'function'` и так же для `GM_getValue` / `GM_setValue`.
`declare const GM_*` живёт в этом модуле, а не в `src/types.d.ts`: ядро не может сослаться на GM API даже по ошибке.

Настройки в менеджере лежат под тем же ключом `amo-stickers:settings`, объектом. Если в менеджере ключа нет, а в
`localStorage` есть настройки прежней версии, первое `getSettings` переносит их в менеджер и удаляет из
`localStorage`; битый JSON удаляется без переноса. Запись с менеджером идёт только в него.

### Хранение

IndexedDB `amo-stickers` на домене amo: паки (`tg:<имя>` для импорта, `custom` — свои стикеры), стикеры (готовые
GIF-блобы; у своего стикера — ещё подпись `caption`, с которой нарисован GIF: из неё метка имени файла) и недавние.
Недавние делятся по видам — стикеры (`l:<id>`) и GIF (`r:<источник>:<id>`) — и ведутся порознь: до 40 каждого вида,
повторная отправка поднимает элемент наверх, «Очистить» и «Убрать из недавних» трогают только свой вид. Настройки —
через `Host`.

Режим попапа хранится не в `Host`, а в `localStorage` страницы под ключом `amo-stickers:mode` (`pickerMode.ts`): это
удобство интерфейса, и сбой чтения или записи не выходит наружу — без режима он выбирается по библиотеке.

### Внешние данные

Всё, что пришло из сети, проверяется на границе (`core/net.ts`):

- запросы — только `https` к `api.telegram.org` (точно, без поддоменов), `giphy.com` и `klipy.com` с их
  поддоменами, по разобранному `URL`; та же проверка на итоговом адресе после редиректа. Service worker отвечает
  только content script-ам своего расширения;
- `Host.fetchJson` возвращает `unknown`: форму ответа сужают гарды в `sources/*.types.ts`. Элемент выдачи с
  непригодными полями или ссылкой вне политики отбрасывается, битый ответ целиком — ошибка источника;
- версию GIF для отправки `sources/gifs.ts` выбирает по весу, который источник сообщает у каждой версии (`size`:
  строка у GIPHY, число у KLIPY): самая тяжёлая из не больше 2 МБ, иначе самая лёгкая из не больше 8 МБ, а если
  тяжелее 8 МБ все — самая лёгкая, и её скачивание оборвётся на лимите. Кандидаты — GIF-версии от
  крупной к мелкой (GIPHY — от `original` до `fixed_width_small`, KLIPY — `gif`, `mediumgif`, `tinygif`, `nanogif`,
  их же запрашивает `media_filter`), с весом, прошедшие гард и политику; равный вес — первая по списку. Вес — не поле
  формы: версия без веса или с непригодным весом элемент не отбрасывает, а если веса нет ни у одной, версия
  выбирается по имени (`downsized`, затем `original` у GIPHY; `gif`, затем `tinygif` у KLIPY);
- `Host.fetchBlob(url, maxBytes)` читает тело потоком и обрывает его на лимите (в расширении — внутри SW):
  GIF из поиска — 8 МБ, файл стикера Telegram — 5 МБ. Лимит GIF (`MAX_REMOTE_GIF_BYTES` в `net.ts`, читает
  `app.ts`) — защита на случай, когда вес из выдачи неизвестен или расходится с фактом. В userscript с менеджером
  потока нет: запрос обрывается `abort()` по `Content-Length` на заголовках или по `loaded` в `onprogress`, а ответ
  без них — на `onload`. Не-2xx статус важнее лимита: какие бы колбэки ни позвал менеджер, ошибка — `HTTP <код>`,
  тело сверх лимита не дочитывается, в тексте — то, что успело прийти. Ошибки политики, лимита и HTTP у всех
  окружений общие — из `core/net.ts`; политика и лимит — `LocalizedError`, чтобы отказ SW показывался на языке amo
  («Язык интерфейса»);
- `file_path` Telegram — без `..`, иначе URL схлопнется и запрос с токеном уйдёт в другой метод Bot API;
- `.tgs` распаковывается не больше 8 МБ и проходит `isLottieJson`; GIF из поиска перед вставкой — `inspectGif`.

### Что писать об amo

В публичных файлах (код, комментарии, тесты, дока, OpenSpec, CLAUDE.md) об amo — только наблюдаемое поведение страницы
и то, что видно в её бандле и рантайме (`sendRequest`, `reduxStore`, `state.dialogs`, форма сообщения очереди): без
путей к исходникам amo web и имён его внутренних функций. Заметки по исходникам — в `CLAUDE.local.md`, он в
`.gitignore`.

## Тесты

Стек — vitest, проект `unit` (`tests/**/*.test.{ts,tsx}`, окружение `node`). Тесты лежат плоско в `tests/`,
хелперы — в `tests/helpers/`. Юнит-тестами покрывается любой важный код с логикой — ядро, скрипты сборки и CI; всё,
что завязано на DOM amo и отправку, проверяется на стенде `dev/harness.html` и в живом amo:

```bash
python3 -m http.server 8777 -b 127.0.0.1
open http://127.0.0.1:8777/dev/harness.html
```

Гейт коммита гоняет только тесты по изменённым файлам (`vitest --changed`); полный прогон — `pnpm test`.

**Правило: без Node API в TypeScript.** Код и тесты на TypeScript (`src/`, `tests/`) не используют Node API —
`node:*`, `Buffer`, `process`, `__dirname`: типов Node в проекте нет, `tsconfig.json` подключает только
`types: ["chrome"]`. Вместо них — Web API из lib DOM, которые есть и в Node: `crypto.subtle`, `atob` / `btoa`,
`TextEncoder` / `TextDecoder`, `CompressionStream`, файлы — через `import.meta.glob` и импорт с `?raw`, а не `fs`.
Локальный `pnpm typecheck` нарушение может не поймать — типы Node иногда подхватываются транзитивно из
`node_modules`, — и оно падает только в CI. Node API остаётся в `.mjs` вне проверки типов: `build.mjs`,
`scripts/*.mjs`.

## Линтинг

```
eslint.config.mjs        # flat config: typescript-eslint + prettier + jsdoc + simple-import-sort + unicorn +
                         # react-hooks и jsx-a11y на **/*.tsx
.lintstagedrc.mjs        # eslint --fix / prettier --write по staged-файлам
.husky/pre-commit        # lint-staged + tsc + vitest --changed параллельно
```

Осознанные послабления:

- `no-undef` выключен для TS: необъявленное имя ловит `tsc`.
- `no-console` разрешает `warn` и `info` наравне с `error`: код исполняется в чужой странице amo, консоль —
  единственный канал диагностики.
- `local/**` в eslint игнорируется: каталог в `.gitignore`, в нём локальные заготовки вне tsconfig.

Границы — `no-restricted-imports`:

- `src/core/**` не импортирует из `src/userscript/` и `src/extension/` — ядро знает только контракты
  `core/host.types.ts` и протокол агента `shared/pageBridge.ts`, а окружения подключают к ним свои адаптеры и агента;
- `src/shared/**` не импортирует ничего вне `src/shared/`: его берут и ядро, и окружения, и агент;
- `src/page/**` импортирует только `src/page/` и `src/shared/` — иначе в агента, который уходит в мир страницы, утянется
  ядро.

`.claude/hooks/lint.sh` — PostToolUse-хук: после каждой правки гоняет по файлу eslint (+`tsc --noEmit` для `.ts`/
`.tsx`). Ошибки в правленом файле блокируют правку.

## CI и релизы

GitHub Actions, Node и pnpm ставятся из `.mise.toml` (`jdx/mise-action`) — те же версии, что локально.

Окружение ставит `.github/actions/setup`: зависимости корня и доки (`pnpm -C docs install --frozen-lockfile`) — во
всех заданиях, eslint и typecheck без зависимостей доки упали бы на импорте vitepress.

- **PR в `master`** (`ci.yml`): отдельные статусы `lint` (eslint + prettier), `typecheck`, `test` (полный прогон, а
  не `--changed`), `build`, `docs` (`pnpm docs:build`: битая ссылка ловится до публикации), `version`. Новый коммит
  в PR отменяет прогон старого. Сборка PR лежит артефактом `build` прогона: `amo-stickers.zip` и
  `amo-stickers.user.js` — для ручной проверки до мержа.
- **`version`** падает, если версия в трёх местах расходится, а в PR, который меняет файлы продукта, — ещё и если
  она не выше версии `package.json` в `master` (`scripts/check-version.mjs --base origin/master`, сравнение по
  числам). Файлы продукта — `src/`, `build.mjs`, `tailwind.config.ts`, `tsconfig.json`, `package.json`,
  `pnpm-lock.yaml` (`PRODUCT_PATHS` в `scripts/version.ts`).
- **Мерж в `master`** (`release.yml`): те же проверки, затем тег `v<версия>` и GitHub Release с `amo-stickers.zip`
  (`manifest.json` в корне) и `amo-stickers.user.js`, заметки — автогенерация по PR. Имена файлов без версии: дока,
  README и `@updateURL` ссылаются на `releases/latest/download/<файл>`, и ссылка не меняется от версии к версии. Если тег уже есть, релиз пропускается с
  предупреждением, прогон зелёный: PR без подъёма версии релиза не даёт. Если push мержа не создал прогона
  (GitHub изредка теряет событие), релиз запускается вручную — `gh workflow run release.yml --ref master`; с другой
  ветки прогон пропускается целиком.
- **Дока** (`pages.yml`): пуш в `master`, меняющий `docs/**` (или окружение, корневой `package.json` со скриптом
  `docs:build` и сам workflow), собирает сайт и публикует его на GitHub Pages без релиза и подъёма версии; упавшая
  сборка до деплоя не доходит. Идущая публикация не отменяется.
- **Claude Code** (`claude.yml`): `@claude` в issue, комментарии, ревью или комменте ревью запускает
  `anthropics/claude-code-action` — ответ в треде и правки в ветку. Авторизация — секрет `CLAUDE_CODE_OAUTH_TOKEN`
  (`claude setup-token`), окружение — `.github/actions/setup`, из команд разрешены `pnpm lint`, `test`, `typecheck`,
  `format`.

## Воркфлоу задачи

Одна задача — один issue, одна ветка, один PR: issue (поиск дублей, связи) → ветка от `master` → спека OpenSpec,
если задача меняет файлы продукта → правки, подъём версии и PR → аудит inline-комментами → правка комментов →
повторный аудит и резолв → архив OpenSpec → мерж. Команды, правила подъёма версии и формат аудита — в проектном
скилле `task-workflow` (`.claude/skills/task-workflow/SKILL.md`): любая задача с правками в репозитории начинается с
него, до первой правки.

Скилы и команды OpenSpec (`.claude/skills/openspec-*`, `.claude/commands/opsx/`) генерирует CLI, и их текст зависит
от его версии. Версия закреплена точной в devDependencies (`@fission-ai/openspec`), поэтому перегенерация — только
`pnpm skills:update`, а не глобальный `openspec update`: иначе скилы разъедутся с версией у соседа. Обновление
скилов — поднятие версии пакета и `pnpm skills:update` в одном PR. Набор workflow берётся из глобального профиля
OpenSpec (`openspec config profile`), в репозитории его не закрепить.
